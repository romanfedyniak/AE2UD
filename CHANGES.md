# Changelog

All notable AE2UD changes are grouped by the version in which they first appeared.

## Important compatibility notice

- AE2UD is not compatible with worlds created with AE2 Unofficial Extended Life.
- Addons made for standard AE2 or AE2 UEL are not compatible unless they explicitly support AE2UD.
- AE2UD is a heavily reworked, API-breaking fork and is not a drop-in replacement for another AE2 build.
- Back up the world before installing or updating the mod.

## Unreleased

### JEI

- **Everything that happens outside a machine has a recipe screen now.** Five of them were paragraphs of text sitting on an item: fluix made by dropping three things in a puddle, the entangled singularity made by blowing one up, and a crystal seed grown in water, one line each per crystal. They are categories with slots now, so what goes in and what comes out is looked up the way any other recipe is, and the part a grid cannot say - that a liquid or an explosion is what sets it off, that accelerators make growth faster - is written across the top of the entry, wrapped to the panel and given as much room as it needs rather than measured against the English: the same sentence is longer in most other languages. Three more describe things that were written down nowhere at all: the Charger, which turns certus quartz charged and fills any tool that holds power; the ME P2P Tunnel, whose kind is chosen by whatever you right-click it with; and the Entropy Manipulator, which has a table of blocks it heats and cools that a player could only find by trying. The tunnel category is worked out only when it is opened, because listing what attunes a tunnel means offering the registry every item in the game - it answers by mod and by capability as well as by item, so there is no shorter way and no reason to spend it at load. Half the Entropy Manipulator's table is water and lava, which have no item to put in a slot, so those sides are drawn as fluids; heating water gives nothing back, and that entry simply has no output. The new categories have no machine window to cut a background from, so their slots and arrows are cut from the furnace instead - which is what JEI's own vanilla categories do, and what the three older ones here do with the grindstone, condenser and inscriber. Each entry centres what it has in the panel, so one with nothing to explain sits in the middle rather than under an empty line. Upstream AE2 has the same six; the layouts are this fork's, since the mechanics behind three of them no longer exist upstream.

- **Recipe categories can be switched off one at a time.** A new `JEI` section in the client config carries a line per category - the three that were already there and the six new ones - and a category switched off is never registered rather than registered empty, so it leaves no dead tab behind. The Charger has two lines rather than one, because its two halves are unrelated: a player who wants the quartz recipe and not a list of tools being filled can have exactly that. Nothing here changes a recipe; the grindstone still grinds with its category hidden.

- **What is left as plain text is only what a recipe cannot say.** Charged certus quartz still explains that it turns up in caves and sparkles, and the crafting presses still explain that they lie at the centre of a meteorite and that a compass finds one. Neither is a recipe, and drawing them as one would be a lie. The half of the charged quartz note that described the Charger is gone: the Charger draws itself now.

### Fixes

- **Of two patterns making the same thing at the same priority, one was invisible - and which one changed every time the game started.** The index a job searches kept the patterns for a key in a sorted set ordered by priority alone, and a sorted set drops what its comparator calls equal, so the second pattern for an item was never added. Priority defaults to zero, which means this was the ordinary case rather than a corner one: two ways to make the same ingot, and the network only ever knew one of them. Worse, which one survived came out of the iteration order of a hash map keyed by pattern, and a pattern's hash is its encoded item's - which vanilla does not define, so it is an identity hash that differs on every launch. A plan that worked before a reload could come back a simulation after one, with nothing in the world changed. The index is now built in the order patterns are offered and sorted by priority with a stable sort, so equal priorities keep that order instead of being thrown away; the useful half of the old behaviour is kept explicitly, by dropping a pattern only when the same *encoded pattern* has already been offered for that key - so one recipe sitting in ten interfaces is still one way of making it, and so is a pattern naming the same output in two of its slots. The two collections behind the offering order became insertion-ordered for the same reason. Inherited from upstream: GTNewHorizons' fork has the same comparator and the same sorted set.

- `/ae2 meteorites` ignored the range it was given and always listed 2000 blocks. The dispatcher passes a subcommand its own name as the first argument, so the range was read out of the word `meteorites`, which is not a number - and the failure was swallowed into the default.

- **The Interface Configuration Terminal wore a missing texture as an item.** Its model still named the Interface Terminal's face, which was renamed along with the part it belongs to, so the item was drawn with the purple-and-black placeholder - and flickered, because a display part stacks five faces on one plane and they only stay out of each other's way while most of each texture is transparent. A placeholder is opaque everywhere, so it fought all four of its neighbours for the pixel. The part in the world was never affected: it draws only the lit layers, and those were always its own, which is why it already looks unlike the terminal beside it. That front layer is invisible on every part of this family - the model reads a window of it that is transparent in all six of them, and the bezel a player sees comes from another layer - so it now names the same shared texture the others do. An orphaned model file for the debug replicator card, left behind by a rename and loaded by nothing, went with it.

- **Blocking mode never looked at fluids.** It asked the neighbour's item slots and nothing else, so a machine whose slots were empty but whose tank was full counted as free - and a pattern made of fluids was never blocked by anything at all. Blocking now also asks about every key type the pattern actually pushes, through the same registry a storage bus reads a neighbour with. It is named by key type rather than by fluid, so a type an addon registers - a gas, say - is covered with no code of its own, as long as the addon registers how to read a neighbour and not only how to push into one. Only the types a pattern really uses count, so a machine sitting in a coolant no recipe here asks for is still not busy with anything, and an interface carrying no such pattern pays nothing for this. Upstream AE2 has no such hole because its blocking reads the neighbour generically to begin with; GTNewHorizons' fork closes it only for its separate fluid interface, which is not a distinction this fork has - one interface serves every type here.

- **The wheel did nothing over a level emitter's filter.** Shift and the wheel step the amount on every other fake slot in the mod - an interface's stock, a pattern's ingredients - and Ctrl with them halves or doubles it. The emitter's filter took the same gesture and threw it away: the number drawn on that slot is the threshold the emitter watches for, which lives on the emitter rather than in the slot, so stepping the slot's own count changed nothing a type-only slot would keep. The threshold is stepped now, in the unit of whatever is being watched - one item or one bucket a notch, the same units the amount screen types in - and it goes down to zero, which is the emitter's usual setting and one the wheel could not otherwise reach. Nothing is stepped where nothing is drawn: a crafting card leaves the threshold governing nothing, and an emitter watching energy has no filter to read a unit from.

- **An item on a monitor shimmered against itself.** A layered item model keeps its layers thousandths of a texel apart - Forge puts the fluid in a bucket 0.002 in front of the metal and the cover 0.004 - and the monitor flattened the whole model to a ten-thousandth of a block to make it read as a picture, which left those layers fighting for the pixel. A flat model now keeps enough depth for its layers to stay in order, and is centred on the panel rather than placed in front of it, because the face rotation mirrors the depth axis on a wall but not on a floor. Models drawn as blocks are unchanged: they are turned to face the player and are sixteen units deep, so they still have to be squashed to nearly nothing, and their faces are real geometry that never fought. The enchantment glint survives, which it would not have had the depth simply gone unwritten - it is drawn only where the depth equals what the item put there.

- **A monitor can be set to a bucket rather than to what is in it.** Clicking one with a filled container always set the fluid, checking Forge's fluid capability before it looked at the item at all, so there was no way to have a monitor watch the bucket itself. A click now sets whatever is in hand; clicking again with the same item swaps the monitor to what that item contains, and clicking once more swaps back. Which items count as containers comes from the registered container strategies rather than from a hardcoded fluid check, so a key type an addon registers gets this with no monitor code of its own, and an item nothing claims - a Thaumcraft jar, say - simply stays on the monitor as itself. This is how upstream AE2 does it; GTNewHorizons' fork puts the same choice behind a held keybind instead. A conversion monitor set to a container item now trades that item, which is what it says it is watching.

- **A storage monitor read zero, and a fluid one showed nothing at all.** The part sent the client the key it was watching and whether it was locked, but never the amount, so every monitor in the world read "0" - and since a fluid with an amount of zero is not a stack at all, a fluid monitor had nothing to draw and stayed blank. The amount travels with the rest now, and the icon is drawn from the key alone, so a monitor whose network has run out still says what it is watching. The fluid on a crafting monitor was black: it is drawn in a vertex format that carries no lightmap coordinate and never set one, so it was multiplied by whatever darkness the previous draw had left. It also ignored the size it was asked for, which is why it sat too large on a crafting monitor, and it sampled a mirrored three-pixel strip of the fluid's texture rather than the texture - the code mixed up world units and sprite pixels. Fluids on both monitors now wear their own picture, lit and at the right size.

- **Taking a pattern expansion card out of an interface threw the patterns it paid for on the floor.** The rows a card buys are simply hidden once it is gone, and everything past the line was spilled on the ground the next time anyone opened that interface - a loss the player found out about by looking down, if at all. The card does not come out at all now while anything is standing in those rows, and a click that will not take it marks the patterns in the way in red, so it is clear which ones have to be cleared first. The spill is gone from the client side too, where it had been spawning items that never existed on the server.

- An interface the player had renamed lost its picture. The name a machine is listed under and the item drawn beside it come from one place, and a hand-written name replaced both - so the Pattern Access Terminal showed such an interface with nothing beside its name, and the screen that asks where to send a pattern left a hole where the picture belonged. The name is the player's and the picture is still the machine's now: renaming an interface says what it is for without hiding what it feeds.

- The column of buttons beside a terminal had grown to ten - sorting, direction, view mode, search box mode, keeping the search, pick block, terminal style, key types, pins and the wireless mode switch - which is taller than the window they stand beside and, on a small screen, taller than the screen. They are not all the same kind of thing, and now they do not live in the same place: what belongs to the whole client (the search box mode, whether a query is kept, the terminal style) and the rare things that belong to an item or a host (pick block, key types) sit in a drawer behind one button at the top of the column, while everything that works this particular screen - sorting, view mode, pins, "hide stored", "show missing only", "assemblers only", the power unit, saving the plan as an image - stays out where it can be reached in one click. The drawer opens as a column beside its own button, away from the window, the way the search mode panel and the wireless mode switch already open, and it is on all seven screens that carry those settings, so the terminal style is in one place rather than in seven.

- The Pattern Access Terminal was two rows shorter whenever JEI was installed. It reserved forty pixels of height for the item list, which is the one screen in the mod that did - the ME terminal beside it has never counted JEI when working out how many rows fit. That allowance was written before the mod told JEI where its widgets are; JEI moves its own list aside now, so the terminal is the same height either way.

- Everything a terminal draws beside its window - the button column on the left, the view cell panel on the right, the security station's two slots - was pushed 24 pixels down the moment JEI was installed, so the same screen looked different depending on which mods were in the pack, and ran out of room at the bottom 24 pixels sooner. That was written when nothing told JEI where those buttons were and they had to be moved out from under it; the mod reports every one of them as an exclusion area now, and JEI moves aside on its own. The shove is gone. The wireless upgrade plate hung under a hole left by the same 24 pixels - it had been placed against the view cell panel as that panel sat *with* JEI installed, so without JEI there was always a gap - and now sits two pixels under it either way, from a pair of constants the screen that draws the plate and the container that places its slots both read.

- The buttons standing to the right of the Crafting Plan, its tree and the Crafting Status were flush against the window, while every column of buttons elsewhere in the mod leaves two pixels between itself and the edge it stands beside. They leave the same two now, from one named constant rather than from each screen's arithmetic. The tabs along the top are unchanged: those overlap the window on purpose.

- Pressing the terminal style button could press the button under it. The window changes height, so the whole strip of buttons beside it moves - and vanilla walks a screen's button list to the end without stopping once a button's action has run, so the list rebuilt by the press was walked on into and whichever button the new layout had just slid under the cursor was pressed by the same click. In the ME terminal that was the key type selection sitting one place below, which opened a screen nobody had asked for. It only ever happened when the window grew, since a shrinking one moves its buttons back into the part of the list the walk has already passed, and it was waiting on all seven screens that rebuild themselves from a button - the crafting plan and its tree, the CPU, the network status, the ME terminal and both interface terminals. A click is now dispatched over the layout that was on screen when the button went down, whatever the button does, and the screen is laid out again once the mouse event is over.

- A search box was emptied by pressing a button beside it. Laying a screen out again builds its fields from scratch, and a rebuilt field started from what had been kept for the *next* opening of that terminal - so changing the terminal style or the search mode either cleared the box or, with "keep the search" on, filled it with the query from the last time the terminal was closed. The caret, the selection and the keyboard focus went the same way, so typing afterwards went nowhere until the box was clicked again. What is in a field now survives the screen being laid out again, a window resize included, and only a field's first build starts from what was kept - which is what the setting is about: reopening a terminal, not pressing a button inside one.

- The Pattern Access Terminal opened with its **Interface Names** box focused, so the first thing typed filtered by the name of an interface rather than by what is in one - the least useful of its three boxes, and picked by nothing but the order they were written in. The Interface Configuration Terminal beside it focused nothing at all, leaving no way to start typing without clicking first. Both now do what the ME terminal has always done: a box is focused on opening only while the search mode is one of the automatic ones, and it is the first box - recipe inputs, or configured items - not the one about names.

- The Crafting Plan's window was cut off at the bottom right, below the scrollbar: the corner where its right edge steps inward was missing, so the frame ended in mid-air. The footer was sampled from below that step, which is how the rows of an older layout - the "Crafting CPU:" button and the line repeating the selected CPU's storage - had been dropped when the CPU table took over their job. Those rows are gone the right way now: the foot is drawn as its top, one plain row repeated, and its bottom border, so nothing at either end is skipped and the foot can be any height. The Crafting Status, which never skipped anything, is unchanged in shape.

- A sunken well or a text field left its last `drawRect` colour set, so anything textured the screen drew afterwards came out tinted by it - a list drawn beside a window, say, turning grey because the unfocused search box above it had painted its frame in grey. Three call sites reset the colour by hand and a fourth had already forgotten; the well helpers and both text field classes clean up after themselves now, so the next one cannot forget.

- Right-clicking the Crafting Plan tree's search box did not clear it. Every other search box in the mod clears on a right click; that one was written without it.

- Renaming a machine with the quartz cutting knife was not written down. Neither the tile nor the part told anything to save after taking the new name, so it survived only if something else happened to mark the chunk dirty before the world was unloaded. Both save now. Clearing the box and pressing Enter also left a part named with an empty string rather than unnamed, which counts as a custom name everywhere that asks.

- The Quartz Cutting Knife's own screen ignored the mouse. Its name box had no click handling at all, so the caret could not be placed, nothing could be selected, and a right click did not empty it the way every other box in the mod does - the field was simply focused from the moment the screen opened and took whatever was typed. It takes clicks like the rest now, and a right click clears it and tells the server, which that screen needs because it sends the name on every keystroke rather than on Enter.

- A pattern in the Pattern Access Terminal offered `Middle-Click: Modify Amount`, and middle-clicking it sent the server a request it has no answer for. A pattern has no amount to set; the slots on that screen only look like the ones on the Interface Configuration Terminal, which reach an interface's config inventory and where the click means what it says. Both the hint and the click are now asked of the screen rather than of the slot type the two share.

- The Interface Configuration Terminal's buttons jumped for a frame whenever the search changed. Its row buttons were rebuilt while the foreground layer was drawn, which happens after the buttons have already been painted, so what was on screen always belonged to the list from before the last keystroke. They are settled before any layer is painted now, which is where the Pattern Access Terminal beside it has always done it - and the row slots, rebuilt in the same place, no longer lag either.

- The Interface Configuration Terminal's one search box did two jobs at once: it showed an interface whose configured items matched **or** whose name did, and the author had labelled it `Inputs OR names` - a hardcoded English string, the only tooltip in the mod that never reached a language file. Searching for an item therefore also dragged in every interface that happened to be named after it. It is two boxes now, the way its sibling the Pattern Access Terminal has always had three: configured items on the left, interface names on the right, narrowing together instead of widening. Tab moves between them, right-click clears the one under the cursor, and both remember what was in them the same way the single box did. The new box gets the sunken well every other field in the mod wears, cut from the same shape rather than left flat against the window, and the magnifier the texture draws beside a search box.

- A search field that found nothing looked exactly like one that found everything, on every screen but the ME terminal. The terminal had turned its own field red for a query nothing answers since the search rewrite; the cell view, the crafting plan's tree, both interface terminals and the CPU list had not, so the same query told you two different things depending on which window you typed it into. All eight fields do it now, from one pair of colours rather than the two copies of `0xFF5555` that had drifted apart. On the two screens that carry several fields at once the whole set reddens together - one list answers all of them, and pointing at one field as the culprit would be a guess. An empty query is never red: an empty network, or a network with no interfaces, is not a search that failed, which the terminal itself used to get wrong.

- The two windows the mod paints for itself rather than wearing a texture - the pattern preview, and the cell view beside it - had square corners and a flat border, against the rounded corner and the two highlight lines every other window in the game has. They were drawn out of rectangles, which cannot make that shape. The corners, the edges and the fill are now cut from a real one - the Renamer's - into `guis/panel.png`, and any window of any size is assembled out of those nine pieces. The sunken well behind a text field was wrong in the same way, a shade too dark and a pixel out of place; it is measured off the same window now.

- Holding a key in a text field typed one character and stopped, on the screens that had not asked for key repeats: the three search fields of the Pattern Access Terminal, the CPU list's search on the Crafting Status and the Crafting Plan. Backspacing a query meant tapping once per letter. Repeats are asked for once now, by the base every screen in the mod is built on, rather than by each screen that remembers to - which is what the eight that did had been doing, and what four had not.

- A filter slot told a bucket apart from the water in it, but only a bucket. Left-clicking a filter with a filled container sets the filter to the contents and right-clicking sets it to the container itself - and which items count as filled was read straight out of Forge's fluid capability, while every other slot in the mod asks the registered container strategies. So a terminal row and an interface slot understood any key type an addon had registered a container for, and a filter slot understood fluids and nothing else. It asks the same question as the rest now. For fluids nothing changes at all - fluids are one of those strategies - and it is what lets the new click hints say the same thing on every slot.

- The amount drawn on a slot could run out over the slot beside it under a resource pack or a mod that replaces the vanilla font. The figure was cut to four characters and drawn at a fixed size, which fits a 16-pixel slot only because a vanilla digit happens to be six pixels wide - nothing ever asked the font how wide its own characters were. It is asked now: the widest character an amount can use, times how many of them the reading has, and the text is drawn at whatever size keeps it inside the slot. It can therefore only ever get smaller, never wider than before, and with the vanilla font nothing changes at all - four digits fill the slot exactly, as they always did. The cells of the crafting tree are measured the same way. A key type may also format its amounts however it likes now (`AEKeyType.formatAmount` is no longer final) and name the widest reading it can produce (`getWidestSlotAmount`), so an addon shipping its own unit gets one size for all of its slots instead of a size that moves with the number.
- A slot showing a fluid counted it in millibuckets: sixteen buckets read "16K", which is a count of millibuckets rather than an amount of anything the player asked for. Slots read in the type's own unit now - "16B", "150B", "12KB", and "250mB" below a bucket - which is how the crafting tree has always read them. The short form behind this had never been called by anything, and was broken: it abbreviated by magnitude rather than by width, cutting over at 99, so 250 mB came out as "0.3KmB" and a hundred items as "0.1K". It is a width now, four characters with the unit inside them, which is what upstream AE2 means by it.
- Switching a pattern terminal from crafting to processing mode left the processing grid as it was, so a recipe typed into the matrix had to be typed in again by hand. It is carried over now, both ways, under one rule: a copy never overwrites what the side it came from could not hold. A fluid in the processing grid stays where it is whatever the matrix square opposite it holds - entering crafting mode used to destroy it in both grids - and a square holding the same item on both sides keeps its count, so a count typed in processing mode survives the trip. The round trip also used to wipe the matrix, because coming back to crafting mode copied the by then empty processing grid over it. Outputs are not carried across, so a pattern switched over to processing mode has its ingredients and no output, and Encode does nothing until one is typed in. Carrying the grid across the switch at all is how [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial) behaves, where one store serves both modes.
- The recipes that add a mode to a wireless terminal show up in HEI. They were registered as recipes and worked at a crafting table, but HEI carries drawing code for only the four vanilla and Forge recipe classes and quietly drops anything else, so there was no way to find out the terminal and the panels go together. They are drawn now, one entry per mode.
- Setting an amount from the interface configuration terminal left the amount window open with no way back to the terminal. The value was applied, but the way back was named as the panel on a cable rather than read from where the screen had been opened - so from the wireless form of that terminal it pointed at a block that was not there. It now goes back wherever it came from, which is what the same code already did for every other screen that sets an amount.
- Every ME terminal greyed out all of its slots for an instant on opening, most visibly on the wireless one, where the grid is the whole window. Whether the network has power is a value the server sends, and it starts at "no" until the first one arrives - a tick after the screen it belongs to. The screen now waits to be told before greying anything out, so a terminal opened on a network that really is dark still greys; it just no longer says so about one that is not.
- The upgrade slot on the wireless interface terminal sat away from the plate it belongs in, anywhere but the shortest window the terminal style allows. That window stretches with the number of interfaces it lists and moves every one of its slots to match, but the plate behind the upgrade slot was drawn at a fixed height and so only lined up at six rows. It follows the slot now, and stands three pixels clear of the window on both sides that meet it rather than touching. The lower part of that window is narrower than the top of it, and the corner between the two takes two rows to come in; the plate used to start on the second of them, so its top row overlapped the corner and its left edge sat on the window's last column. The plate on all four wireless terminals is also reported to HEI, which never knew about it: it is drawn wholly outside the window, so the item list could cover the upgrade slot and swallow clicks meant for it.
- Icons drawn from the mod's own sheet came up as solid black squares in two places: the marker showing that a crafting CPU is kept for players or for automation, on a CPU far enough into a job to have a progress bar, and every source icon in the crafting plan tree - taken from storage, promised by a level emitter, or missing. Those icons are a small glyph in a mostly empty field, and two separate things switch off what keeps that field invisible: drawing a filled rectangle turns blending off, and drawing an item turns the alpha test off. Either on its own is harmless, and both happened one after the other in exactly those two places. The same left a row plate in the CPU list drawing its bottom row - the gap between rows - as a dark line under any row following one with a progress bar. Every button, label and icon of the mod's own now sets blending up for itself rather than inheriting whatever the last thing drawn left behind: none of the others was visibly broken, but the pattern terminal was one filled rectangle away from it, since its two tab buttons draw an item before its whole remaining column of buttons.
- HEI drew its item list over the setting buttons beside a level emitter, an interface, a bus and every other screen of that kind whenever one of those buttons was greyed out rather than hidden - a level emitter carrying a crafting card greys its level and redstone buttons, and the column reported to HEI came up that much short. The area is measured from where the buttons actually are now, so a greyed one, a gap in the column or an odd spacing all report correctly.
- A level emitter carrying both a fuzzy card and a crafting card drew both of their buttons in the same slot, one on top of the other, leaving the lower one unclickable. Only the crafting one is shown now: while a crafting card is in, the emitter reports whether the network is asking for its item and never reaches the level comparison that fuzzy matching applies to, so the fuzzy button governs nothing.
- The progress bar under a crafting CPU in the CPU list stopped one pixel short of each end of its row plate, leaving a dark speck at either side of it. It runs the full width of the plate now.
- HEI drew its item list over the buttons of four more screens, which never told it they were there: the two beside the Network Status window the network tool opens, the facade toggle in the network tool's own window, and the power-unit button on the Spatial IO Port and on the Wireless Access Point. Two tab buttons went unreported as well - the one back to the terminal on the Crafting Status screen, and the one to the crafting status on every terminal. Every screen that draws something outside its own window has been walked through, and each now names what it draws there. The ME terminal's column was reported by counting its buttons and assuming their spacing, the way the level emitter's was before it broke; it is measured now, like the rest.

- Pinning an item in a wireless terminal wiped the upgrade cards in it. The terminal keeps a second copy of its own cards, saved back whenever a pin changes, and that copy was loaded from the root of the item's tag rather than from the branch the cards are written to - so it was always empty, and always wrote empty over them. It is loaded from the right place now and is no longer written back at all: the screen owns the cards, and this copy is only there to answer for them.

- The search field in the crafting CPU panel was a bare filled rectangle, with none of the sunken frame every other search field in the mod sits in. The frame is painted into the panel texture now, the way the ME terminal's own is, and the field lines up with the block of CPU rows and the scrollbar beside them.

- A memory card copied a bus without its key types. Everything else travels - the filter, the cards, the settings, the priority - so a bus cloned from one that had fluids turned off quietly went on taking them, with nothing on either screen to explain the difference. The selection is on the card now, for a storage bus, an import bus and a terminal alike.

- A pattern terminal took several times longer to open than any other terminal, long enough to be felt as a stutter. A container hands its contents to a screen twice over: once as a single packet holding every slot, and then, on the same call, as one packet per slot that is not empty - the player's own inventory included. The pattern terminal worked its crafting result out again on each of those, and each of those walked the whole recipe registry, which on a pack of any size is mostly recipes matched through the ore dictionary. An empty crafting matrix was the worst case rather than the cheapest, since nothing was ever found to remember and so nothing could be skipped the next time round. A slot arriving now only marks the result as stale, and only if it is one of the nine squares of the matrix and the terminal is in crafting mode; the screen works the result out once, in the frame that is about to draw it. Measured on a world with GregTech, IC2 and Forestry, opening the terminal spent about 185 ms walking recipes before and about 9 ms after. The throwaway grid used for the lookup also named the container as the thing to notify, so each of its nine writes ran a full sweep of that container - on the server, a full comparison of everything the network holds; it uses an empty container now, as the rest of that file already did. Loading a pattern onto the grid sends some seventy slots one after another and paid the same price, so it is cheaper too.

- A pattern terminal flashed the wrong mode for an instant every time it was opened: one left in processing mode came up as crafting before switching over, and one left in crafting mode showed the processing buttons first. Two separate faults that happened to look alike. The container used to hand its fields to the screen before catching up with the terminal they belong to, and the first handover goes out as the window opens - so the screen was told the value the field starts life with rather than the mode the terminal was saved in, and heard the truth a tick later. The catch-up runs first now, so the opening sync already carries the real mode. Separately, which buttons belong to which mode was decided while drawing the foreground, which happens after the buttons themselves have been drawn; a button starts out visible and nothing had hidden it yet, so the first frame showed both mode tabs and the whole processing row at once. It is decided while drawing the background now, beside the code that already places those same buttons there for the same reason.

- A fluid drawn in a slot was baked from scratch on every frame. Turning a texture into a model walks every pixel of every frame of its animation to find the outline, and a still fluid texture is animated and usually greyscale - so a terminal full of fluids did that work for every one of them, sixty times a second. Sampled on a world with GregTech, IC2 and Forestry, it was the single most expensive thing this mod did while a terminal was open, around a tenth of the client thread; it no longer appears in the profile at all. Each texture is baked once and kept for as long as the atlas it came from lives. The list of overrides the model hands the renderer was also being built afresh on every item drawn, and is now built once. Caching the baked model on the override list is the shape [AE2FluidCraft-Rework-Unofficial](https://github.com/Circulate233/AE2FluidCraft-Rework-Unofficial) uses for its fluid and gas packets; it keys on the fluid and so needs a size cap and an expiry, while keying on the texture bounds the cache by the atlas and needs neither.

- A level emitter carrying a crafting card still wore its threshold on the filter slot. The card makes the emitter answer whether the network is asking for that item, and the threshold governs nothing while the card is in - which is why the level and redstone buttons beside it are already greyed out, and why a middle click on the filter no longer opens the amount screen. The number is left undrawn now, and comes back with the card out: it is kept all along, never wiped.

- A formation plane in active mode tried to place what its filter named whether or not the network held any, over and over for as long as it stood there - and a placement is tried by handing the item to the world's fake player and asking the item itself whether it would go down, which is audible for anything that makes a noise being placed. It asks the network first now. The fuzzy path never had the fault, since it only ever offers the plane what the network actually holds.

- A formation plane in active mode carrying a crafting card went back to trying the placement on every tick, and to making the noise of it. The plane asks whether the world can take what it is about to order before it orders anything, and that question was asked by simulating the placement - handing the item to the world's fake player and letting the item itself answer - which is the very thing that was audible before, now on the path that runs precisely when the network holds none of what the plane is meant to place. It reads the flag the plane already keeps for the block in front of it instead, which says the same thing, costs nothing and is refreshed by whatever changes that block. The same went for a delivery: a crafting cpu that cannot hand its result over retries every tick, so a plane with nowhere to put the result ran the item's placement logic that often for as long as the block in front stood there. It now says no straight away and touches the world again only once that block is gone.

- **Everything a player sets for themselves moved to a config file of its own**, `config/AppliedEnergistics2/Client.cfg`: terminal style, search mode, the amount-button steps, the unit power is read in, the CPU list filters, and the switches for tooltips, placement previews and the mod's visual effects. Those are the settings the game writes back to disk itself, as buttons are pressed, and they used to sit in the same file as everything a pack decides - so a launcher that keeps `AppliedEnergistics2.cfg` in step with the pack could only do it by taking the player's own settings with it, and the only way out was to exclude the whole file. The two are separable now: the pack file holds nothing the game rewrites except the Spatial IO dimension ids, which it picks once and must keep. Nothing is carried over from the old `Client` section, so settings start at their defaults once after updating; the old section is left where it is and read by nothing.

- A processing pattern and a crafting one were the same item with the same icon and the same name, so a wall of interface slots could only be read by hovering over every one of them in turn. They are told apart now: a processing pattern wears the same weave in violet where a crafting one keeps its cyan, and the two are named "Processing Pattern" and "Crafting Pattern" rather than both "Encoded Pattern" - which also makes them searchable as such in a terminal. It is still one item and one encoding; nothing about an existing pattern changes but how it is drawn and what it is called. Violet is the one colour the mod was not already using: amber marks a fake craft and green a job in progress.

- Copying an interface with a memory card lost the last pattern of every row it held. The slots a copy may write to were counted as eight per expansion card plus eight, where an interface has nine to a row - so a full interface with no expansion cards came back one pattern short, and one with three cards came back four short, silently and with the blank patterns for them still in the player's inventory. The count is asked of the interface now, in the one place that already knew it. Three smaller faults in the same copy went with it: a pattern whose recipe no longer decodes - a mod removed, a recipe changed - used up a blank pattern to be re-encoded as the same dead pattern, and is now skipped without spending one; the copy demanded blank patterns in creative mode, where nothing else the card copies costs anything; and the step that hands back a blank for every pattern it clears ran when a wrenched interface was placed back down, which has no patterns to copy and never had. The whole copy also ran on the client as well as on the server, so the blanks handed back and the blanks spent were briefly applied twice to the same inventory, once against a copy the server was about to overwrite; it runs where it counts now. The code doing all of this was duplicated word for word between the interface part and the interface block, so each of these was two faults rather than one; it lives in one place now (`appeng.util.MemoryCardSettings`).

### Amount entry

- The amount window's way back is always there now. The tab in its top right is drawn from whatever the screen was opened on top of - a terminal, a machine, a terminal in your hand - and when that host will not say what it is, the corner was simply left empty and the screen looked like a dead end. Those cases get a plain arrow labelled `Back` instead, which closes the window: the honest answer when nothing will say where you came from, and never the wrong screen to open.

- **The plus and minus buttons take the step you tell them to.** Every screen that types an amount - ordering a craft, setting a fake slot, a level emitter threshold, a machine priority - draws the same four buttons above the field and four below, and each of those screens had its own set of steps in the config, capped so that the first button could never exceed 9. There is one set now, and a modifier key chooses between four of them: unmodified adds 1/10/100/1000 as before, Shift adds 1/16/32/64 (the set modern AE2 offers), Ctrl multiplies and divides by 2/3/5/10, and Alt by 10/100/1000/10000. Each group carries its own operation, so a group that multiplies is a group whose lower row divides. The labels change while a modifier is held, so what a press will do is written on the button before it is pressed; the arithmetic saturates instead of wrapping, a division truncates towards zero, and the result is held inside whatever the screen allows. There is no cap on a step any more - a button that cannot draw its step in full shortens it the way a slot amount is shortened, puts the whole reading in its tooltip, and past that draws it smaller. The three old config keys are dropped from the file when it is loaded.
- **The steps are set in game, not in a text file.** The tab in the top right of the amount window opens a table of them: a row per modifier, a button that swaps that row between adding and multiplying, four steps to the row, and a button that puts the whole table back to its defaults. It writes when it is left - by the tab, by Escape, by the inventory key, all the same - so there is nothing to save and nothing to lose by leaving; a step that does not read as a whole number of one or more is shown in red, and that button keeps what it had. Nothing about it reaches a server, so two players on one world can hold entirely different opinions about what Ctrl does.
- The amount window has a way back to the screen it was opened from, whichever that was. It had one only from the four terminals it knew by name; from a storage bus, a formation plane, an interface or the interface configuration terminal there was no tab in the corner at all, and the only ways out were confirming the amount or Escape. The screen asks the machine it was opened on top of instead of recognising it, so every machine with a screen of its own now labels the way back with its own item.
- **A level emitter no longer carries its own copy of the amount buttons.** It kept a text field, eight buttons, a unit toggle and its own arithmetic to do what the amount screen already does, and sent the threshold to the server on every keystroke. Its filter slot now wears the threshold the way any slot wears an amount, and a middle click on that filter opens the amount screen - the same one, with the same steps, the same modifiers and the same unit toggle, so a threshold on a fluid is typed in buckets exactly the way an amount in a slot is. The value is sent once, when it is confirmed. The window is 44 pixels shorter for it: the field, the sunken well painted behind it and the two rows of buttons were most of what stood between the title and the player inventory, so the filter moved up under the title and everything below it came with it.
- **The priority screen is gone, and the priority tab opens the amount screen instead.** That screen existed to type one number, with its own eight buttons and its own arithmetic beside the two other copies of both; the tab on a drive, a chest, an interface, a storage bus or a formation plane now goes straight to the amount screen, which shows the machine the priority belongs to and takes negative priorities as it always did. As with the emitter the value is sent once, on confirmation, rather than on every keystroke - so the intermediate 1, 12 and 123 on the way to 1234 no longer land in the network and rebuild its priorities three times over.

### API

- **A pattern's input slots answer as one thing instead of three.** `getSubstituteInputs(slot)`,
  `isContainerFabricated(slot)` and `getCondensedInputs()` are gone, replaced by `getPatternInputs()`:
  `get(slot)` hands back everything about that slot - what may stand in for the encoded ingredient, most
  preferred first, and whether the network assembles that slot's container out of a key rather than pulling
  it from storage - and `getCondensed()` gives the totals one craft consumes. The three were always read
  together and meant nothing apart, and scattering them meant a caller could consult one and forget the
  next; the crafting cpu had to ask the pattern four separate questions about a single slot before it could
  fill one square of a table. Nothing about what a pattern does has changed, and both halves are still
  worked out once and kept, which the cpu depends on - it reads the condensed totals on every tick a job is
  running. Registered as amendment 45. This is the shape a pattern will be normalised through when the
  crafting calculation is rewritten, and where a slot's durability and returned container will live.

- **A network machine can say it holds patterns**, through the new `IPatternContainer`, and the Pattern Access Terminal lists whatever says so. It used to name two classes - the interface block and the interface part - so a machine from an addon that kept its own patterns could not appear in it at all, however much it behaved like one. A container answers with its pattern inventory, how many of those slots it has actually paid for, what to call it and draw for it, where it stands, and whether it would work a given pattern at all; everything else has a default, so implementing it is two methods. That last question is the interesting one: an interface says yes to a processing pattern anywhere, but to a crafting pattern only when something beside it will take plans, which is the only route there is from a network to a molecular assembler. Nothing in the mod behaves differently yet - the interface is still the only thing that implements it - and it is deliberately the smaller half of what upstream calls `PatternContainer`, with the same method names where the job is the same, so the rest can arrive later as defaults rather than as a rename.

- An upgrade card is described by what it confers rather than by which item it is. A card names one or more `CardTrait`s and how many points of each it carries (`IUpgradeRegistry.registerCard`), a host declares the traits it takes from anyone's card (`addTraitSupport`) and may cap one (`setTraitLimit`), and everything else asks the same three questions: `getInstalledPoints(trait)`, `isInstalled(trait)`, and `canInstall(card)` for whether one more would do the host any good. Speed and capacity are two ordinary traits now - `CardTraits.SPEED` and `CardTraits.CAPACITY` - and the twelve methods that named them are gone, along with `getInstalledSpeedPoints()` and `getInstalledCapacityPoints()` on the two upgradable-host interfaces. An addon can name a trait of its own, and, which is the point of the change, hang its card on one of AE2's: a single card can stand in for two, which no amount of comparing items allows. A trait only counts where the host declared it, so a card does not smuggle an effect in by fitting through some other trait, and the rule for whether a card may be installed lives in exactly one place. Nothing a player can see changes - the cards AE2UD ships work as they did.

- Every card AE2UD ships is described that way, not only speed and capacity: fuzzy, inverter, sticky, equal distribution, overflow destruction, crafting, fake crafting, redstone and pattern expansion are traits now, and the sixty-odd places that recognised them by comparing one item against another ask the host or the inventory instead. Two cards stay as they were, because neither is a property of the host it sits in: the magnet card, which is taken out as a stack to read its own filter and its own cards, and the quantum link card, which lives in a machine's own slot rather than in an upgrade inventory. A consequence worth naming for anyone writing an addon: a cell reading a card that carries several of these at once now takes all of them, where the old chain of alternatives stopped at the first one it matched. Shift-clicking a stack of pattern expansion cards into an interface goes through the same rule as every other card now - the special case that named that one card by hand, in the container every screen shares, is gone. A cell from another mod that never registered its own upgrade support is the one thing this can catch out: it used to get fuzzy matching because the card was AE2's card, and now has to say it takes the trait.

### Autocrafting

- **The solver understands a pattern that feeds itself.** Still wired to nothing; still only tests. A cycle
  used to be recognised and stepped around, which had a defect worth naming: the ordering stops at the first
  cycle and leaves *everything behind it* unplaced, not only the loop - so a step below one lost its pattern
  too and was reported missing while its ingredients sat in storage. The graph is now condensed into
  components when, and only when, a cycle is actually found, so what is below a loop is settled the ordinary
  way. A pattern that consumes some of what it makes is then run by dividing rather than by going round:
  each craft nets the difference, so the shortfall divides out once and a request for ten billion through a
  loop is answered as fast as a request for one - the shape that used to hang, at the size at which it hung
  worst. Nothing starts from nothing: a loop needs one craft's worth of its own output in hand, that seed is
  held back from being spent on the order itself, and a loop with no seed and nothing to make one is reported
  rather than attempted. A loop that gives back no more than it took is not treated as a source at all,
  because running it is a way of losing the thing. The same rule settles catalysts, which are the commoner
  half of this: what a pattern hands back is not something it consumed, so a mould that goes in and comes out
  is asked for once rather than once per craft, and is not counted as made either. A loop running through
  several different things is recognised and left alone for now; solving one wants more than the single
  division a self-feeding pattern needs, and it will get its own change.

- **A crafting plan solved on a graph rather than a tree.** Nothing uses it yet - the calculator a job runs
  through is unchanged - but the thing that will replace it is here and is tested. A node is a *thing* rather
  than a *request for a thing*, so the cost is the number of patterns the request can reach and the amount
  ordered does not enter into it: one of something and ten billion of it are solved in the same work, which
  the tests assert rather than claim. Keys are put in an order where every consumer of a thing is settled
  before the thing itself, so the whole demand for it is known at once - that is what lets storage be handed
  out on the full picture instead of to whichever branch was walked first, and it is why the answer no longer
  depends on the order slots happen to be written in. A pattern that runs out of an ingredient is held to what
  it managed and the next pattern for that key takes the rest, which is the spill the old tree did one craft
  at a time. A byproduct is credited to a ledger and settled after the output its pattern was chosen for, so
  the step that wants it finds it already made instead of crafting it again. Scarce storage goes first to a
  slot that has no alternative, since a slot with a choice can be sent elsewhere. Arithmetic is checked rather
  than saturated: an order that will not fit in a plan is refused outright, because a saturated plan looks
  finished and is nonsense. The ceilings are on the *shape* - how many things are reachable, how many
  connections between them - and never on the number of crafts, which would take away the ten-billion order
  for nothing. A cycle is recognised and left alone for now rather than looped over; making it productive is
  the next step. The tests run without Minecraft at all - no world, no registries, no items - which is the
  point of where the line was drawn: below the phase that resolves a pattern there is nothing but keys and
  longs. A container a craft hands back is counted as something that craft made, alongside the result: kept
  off to the side it would be spent by a step running before the one that gives it back, which adds up and
  cannot happen. An ingredient may also be measured in uses rather than in whole items, so a tool lasting
  sixty crafts is two tools for a hundred rather than a hundred stages of wear - nothing asks for that yet.
  Ten thousand patterns deep solves in 77 ms where the old tree would have run out of stack, and
  twenty-four levels of branches that share their inputs - sixteen million nodes to a tree - in under a
  millisecond.

- **A crafting test rig, so a change to the planner can be checked instead of remembered.** A developer block that is a whole ME network on its own - the storage, the power and the only machine on it, a machine that accepts every pattern and really performs it - so a test starts by placing one block and a crafting cpu rather than by building a network. `/ae2 craftingtest` runs fifteen scenarios through it: a plain chain, two branches meeting on one leaf, a preferred pattern running out of its ingredient and spilling onto the next, the same pair left at equal priority, a request nothing can satisfy, a forced start, a level emitter, a pattern making both ingredients of the next one, a pattern that eats its own output, a forty-step chain, two hundred branches feeding one output, the same question asked for one and for twenty thousand, and a plan actually handed to a cpu and watched until it is done. Each one records what the planner answered - whether it came back a simulation, the byte total, and the three plan counters - and the run reports how that differs from the answers recorded as right, line by line. Each is planned up to five times and the middle time reported, because the first answer of a session pays for the just-in-time compiler and can be two orders out; the time is reported and never compared, since a slower machine has not changed an answer. `/ae2 craftingtest baseline` records the current answers as those; naming scenarios runs only those. Recording is a separate word on purpose, because a baseline is an agreement that today's answers are correct and nothing should be able to make that agreement by accident. Nothing here is read by the mod: the block is behind `UnsupportedDeveloperTools` and the baseline lives in the config folder.

- **Co-processing units come in four sizes above the first.** A Quad Core, a 16 Core, a 64 Core and a 256 Core unit, each built out of four of the one below it, and each worth that many parallel operations on its own - so a CPU that used to need two hundred and fifty-six blocks to run 256 crafts at once now needs one. The block is still a co-processor in every other way: it forms part of the same multiblock, and a CPU counts what its blocks are worth rather than how many there are. The tier shows in the pattern inside the block and, on a formed CPU, in how much of the face is lit: a point of light that grows into a disc and then fills the whole face. The family keeps its purple, since colour on a crafting cube already means storage size. `Features.CraftingFeatures.HighCapacityCoProcessors` turns the four off and leaves the original. Taken from [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial), including the patterns its own tiers wear.

- **The Crafting Status, the Crafting Plan and a crafting CPU's own screen have a search box.** A large job fills several screens of rows, and the only way to find one thing in it was to scroll. It reads the same grammar every other box in the mod does - `"iron ingot"`, `iron | gold`, `-stone`, `@mod`, `#tooltip`, `$oredict`, `&id`, `/regex/` - and takes a name from an item on the cursor or dragged out of HEI, like the rest. It narrows what is shown alongside the Hide Stored button rather than instead of it, and a row it hides keeps counting: turn the query off and it comes back with its amounts intact. To make room for it the header keeps only the screen's name: the elapsed time and the byte count moved down to a line of their own, centred above the buttons they belong with. Both windows grew at the foot to hold that line, which their textures had no room for - the Crafting Status by nineteen pixels and the Crafting Plan by fourteen, which is what it took to leave them the same shape. The boxes are 118 wide, wider than the terminal's.

- The Crafting Plan's tree read its search as one lowercase substring of a name and nothing else. It reads the same grammar the ME terminal does now, out of the same code: `"iron ingot"` as one term, `iron | gold` for either, `-stone` to leave something out, and the `@` mod, `#` tooltip, `$` Ore Dictionary and `&` registry-name channels, plus a `/regex/` term. Hovering the field lists all of it - the tree's box had no tooltip at all before - and it holds a hundred characters instead of the thirty-two a query of this shape runs out of.

- The Crafting Plan window has stopped repeating the selected CPU's storage and co-processors along its bottom edge. The CPU table beside the window already draws both on the row they belong to, and spells them out again in that row's tooltip, so the line carried nothing the screen was not saying twice elsewhere. The window is sixteen pixels shorter without it, which also means one more row of the plan fits on a screen of the same height. The word "Simulation", which shared that line, moved up into the title, which it now replaces: an incomplete plan reads "Simulation - 1,234 bytes used" where a complete one reads "Crafting Plan - 1,234 bytes used". It stands in for the title rather than beside it because the two together run past the edge of the window, and because that is the first thing to say about such a plan. It is shown only once there is a plan to call incomplete - the old line put it there for the first frames of every plan, while the header beside it still read "Calculating...", because the field behind it reads as a simulation until the server says otherwise.
- **The Fake Crafting Card.** An interface carrying it finishes a pattern the moment it is handed over: nothing is expected back, and the job closes as if the results had arrived - for a machine chain that carries its own outputs, or one that consumes them. Nothing is created, so the card is a way to run a chain, not a way to make items. The idea and the card's name come from two LGPL forks that each ship their own version of it: [NAE2](https://github.com/AE2-UEL/NAE2), where it is the Job Auto-Complete Card, and [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial), where it is the Fake Crafting Card. Both reach it by mixin; here the medium answers for itself, so an addon's own pattern provider can do the same through `ICraftingMedium.isFakeCrafting()`. Turn the card off entirely with `FakeCraftingCard` in the config's `NetworkFeatures` section.
- **A fake pattern is a last step, and only a player can order it.** It is never used as an ingredient of another pattern - the step after it would wait forever for something that is never made - and a craft ordered by a machine, an interface with a crafting card or an export bus, will not use one either: that machine waits for a delivery that is not coming, and would order the same job again, forever. Such a craft simply does not start, the way any craft with no pattern behind it does not start. A pattern that also sits in an interface without the card keeps working normally everywhere, and the crafting CPU will not hand that copy to the carded interface unless it is the step that ends the job.
- Everywhere a key is shown, it is marked. In the Pattern Access Terminal an interface with the card has its whole row of pattern slots tinted amber - the card is in the interface rather than in any one pattern, so marking each of its up to thirty-six slots would say the same thing thirty-six times. Everywhere else it is the craftable "+" that turns amber instead of white, and it turns wherever that mark is already drawn: on an ME Terminal row, on a pattern terminal's ingredient and output slots, and on a recipe's ingredients in HEI. An ME Terminal row also says "Fake Craft" in its tooltip.
- A crafting plan that came up short can now be started anyway: the Start button reads **Force Start** when the network cannot supply everything, on the Crafting Plan screen and on the Crafting Tree alike, and pressing it plans the job again treating what is lacking as promised. The CPU takes the job and waits for those ingredients to be put into the network, the same way it waits for a level emitter's share, then carries on. The plan still lists what is missing, so it says what has to be brought. The mode is named `CraftingMode` after [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial); the approach is adapted from [RandomComplement](https://github.com/Circulate233/RandomComplement).
- **A formation plane takes a crafting card.** An active plane whose filter names something the network does not have orders it to be crafted, and puts down what comes back - so a plane can build from a pattern rather than from what happens to be in storage. A second button beside it, the same "craft only" the export bus has, tells the plane never to take the ready-made and always to order. Both buttons wait on the active mode as well as on the card: a passive plane is storage that is pushed into and has nothing to order. It orders exactly one placement's worth at a time - one block, one bucket, or a whole thrown stack where acceleration cards apply - because a plane that has just put a block down is blocked until somebody takes it away, and anything ordered beyond that would sit in the cpu with a job that never closes. If the space is taken by the time the craft arrives, the plane refuses the delivery and the cpu offers it again, so it places itself as soon as the way is clear. The card also brings the craft priority button, as it does everywhere else it can be inserted. Taken from [ExtendedAE](https://github.com/GlodBlock/ExtendedAE), whose Active Formation Plane carries the same card.
- The Crafting Status screen tells the two apart: a row a machine is working on still reads **Crafting**, while one the CPU can only wait for - a level emitter's promise, or what a forced job was short of - reads **Waiting**. Both used to read Crafting, which was wrong for a level emitter long before Force Start existed and made it common. A waiting row is tinted orange rather than the green that marks work in progress, and orange wins over both green and yellow on a row that is partly each: those two say the network is getting on with it, and orange says it cannot until someone brings the rest.
- The list of crafting CPUs beside the Crafting Status, Crafting Plan and Crafting Tree screens can be searched and filtered. A search field in the panel's header matches a CPU by its name - or by the name of what it is crafting, so "who is making iron" is a question the list can answer - and four buttons above the panel narrow it further: show every CPU or only the busy or only the idle ones, show only those set to take player or automation requests, and order the list by name, by crafting storage or by co-processors, ascending or descending. All four are remembered between sessions; the search text is not. The CPU currently selected is always shown, whatever the filters say, so a job is never sent to a processor that has been filtered out of sight.
- A crafting CPU can be renamed with the Certus Quartz Cutting Knife, which every other AE block already allows. A formed and powered CPU used to swallow the click and open its own screen instead, whatever was held, so the only way to name one was to name a crafting unit in an anvil before placing it. A CPU's name is still the names of all its named blocks joined together, so name one block to name the whole thing.
- The Crafting Tree puts Start where the Crafting Plan screen puts it, against the right edge of the window rather than the left, and gained the **Cancel** button it never had, against the left edge. Cancel steps back to the amount screen the job was ordered on, or out to the terminal when no amount screen preceded it, exactly as it does on the plan screen.
- A crafting CPU that refuses to form now says why, over the hotbar, to whoever placed the block that broke it. Four reasons are covered: the CPU is larger than the size limit, it reaches into a second chunk while that is forbidden, it is not a solid box of blocks, and it holds no crafting storage. All four used to fail in silence, leaving nothing but blocks that would not join up - and the hollow-box case did it by throwing an exception that was caught and discarded.
- The size a crafting CPU may reach is configurable per axis, through `maxSizeX`, `maxSizeY` and `maxSizeZ` in the config's `craftingCPU` section, from 1 to 64 blocks. The default is 17, which is what AE has always allowed - the old limit read as 16 in the code but let a seventeenth block through. Raising it is not free: every recalculation walks the whole box, so a much larger CPU costs more each time one of its blocks changes.
- A crafting CPU can be required to fit inside a single chunk, through `requireSingleChunk` in the config's `craftingCPU` section. It is off by default and nothing changes while it is off. Turned on, a multiblock reaching into a neighbouring chunk does not form at all - the same refusal a CPU larger than the size limit already gets - and one already built across a chunk border falls apart the next time it is recalculated, on the next block update or chunk load there.
- `ICraftingGrid.beginCraftingJob` takes a `CraftingMode`, and `ICraftingJob` reports the one it was planned in.
- **A crafting job carries a priority.** When several jobs are running and more than one of them wants the same machine - one compressor, one furnace behind an interface - whichever CPU the network happened to reach first took it, and that order was whatever a hash set handed over: not chosen, not the same in two worlds, and impossible to influence. A job now carries a priority, a whole number that may be negative and defaults to 0, and a machine that comes free is offered to the highest priority job waiting for it. Jobs of equal priority take turns, one step a tick, so two background jobs on one machine no longer leave one of them permanently behind the other. The same order decides who gets first refusal on an item arriving in the network, so a job served first at a machine is also served first with what comes back from it. Priority orders and does nothing else: it does not choose which CPU takes a new job, and a job with nothing to compete against runs exactly as fast at -5 as at 0. It stays with the job for as long as the job runs, is saved with it, and returns to 0 when the job ends or is cancelled; raising it does not take back a pattern a machine has already begun, it decides who gets the next free one. The number is typed on the same amount screen every other number in the mod is typed on, and it is set in four places: beside Start on the Crafting Plan and on the Crafting Tree, which share it, so an order can be given one before it is started; beside Suspend on a crafting CPU's own screen and on the Crafting Status, which change a job already running - the same right Cancel beside them already has; and in the left-hand column of an ME Interface and an Export Bus, under the button the crafting card adds, so what those two order for themselves is worth what you say it is. That screen is drawn over the one that asked for it rather than in its place, so a crafting plan that cost a whole calculation to work out is not thrown away to type one number. A CPU's tooltip in the crafting status list says what it is running at, unless that is 0. The idea is [AE2CraftPriority](https://github.com/yuhhamu/AE2CraftPriority)'s.
- `ICraftingGrid.submitJob` takes a priority, and `ICraftingCPU` reports the one it is running at.

### Config

- Every number behind an upgrade card is in the config now. `upgrades.cards` says how many of a card fit in a machine, part, cell or tool wherever more than one does - `energy.portable_cell`, `capacity.part.bus.import`, `speed.molecular_assembler` and so on - and zero there refuses the card outright. Only the cards a second of which adds to the first are listed: acceleration, capacity, energy and pattern expansion. The rest - fuzzy, inverter, sticky, equal distribution, overflow destruction, crafting, fake crafting, redstone, magnet and quantum link - mean the same whether one or three are in, so there is nothing about them to tune. `upgrades.points` caps how many points of an upgrade a host will take however many its cards carry. Every one of those is zero - no cap - to begin with, because AE2's own cards are worth a point each and are already limited by how many fit; a cap only starts to mean something once an addon ships a card worth several, and whether that is too much is the pack's call rather than the mod's. `upgrades.cardPoints` says what one card is worth wherever it is installed, including the cards that only ever go in singly, because what a point means there is an addon's to decide. And `energyCard` says how much of each machine's own capacity one energy card adds: eight for a portable cell, a matter cannon and a colour applicator, one for a wireless terminal, a half for the vibration chamber. The file writes itself on the first run with every entry at the value the mod shipped, so nothing changes until something is edited. All of it needs a restart, which the entries say.

### Energy

- The **Crystal Resonance Generator** is here, from [modern Applied Energistics 2](https://github.com/AppliedEnergistics/Applied-Energistics-2): a block that makes power out of nothing, at 20 AE/t by default. Only one of them runs on a network, however many are built - the rest are held quiet, and quartz fibre does not get around it, since the grids a fibre ties together count as one for this. A suppressed generator says so in Waila and The One Probe. It asks for no channel and keeps generating while the network is dark, so it can bring a network that ran out of power back on its own. It joins the grid through the face it stands on, so it goes onto a cable or a machine, and the rate is configurable through `rate` in the config's `crystalResonanceGenerator` section, where zero turns it off. Crafted from gold rather than the copper modern AE2 asks for, since 1.12 has none: four gold ingots, a block of fluix, a charged certus quartz crystal and three iron ingots.

- The **Energy Card** is here, from [modern Applied Energistics 2](https://github.com/AppliedEnergistics/Applied-Energistics-2): it enlarges the battery of the tool it is installed in. Two fit in a portable cell, a matter cannon and a colour applicator, and each is worth eight times the tool's own battery, because the card is crafted from an advanced card and a dense energy cell and a dense cell holds eight times a plain one - so a portable cell with two of them carries seventeen times what it carried empty. They go in through the Cell Workbench, in the slots those three tools already had, and they compete for those slots with the cards already there rather than adding new ones. Pulling a card back out leaves the tool no fuller than its smaller battery allows, so charge above the new maximum is lost.

- The **Vibration Chamber** takes three of them, its first upgrade of any kind, and each is worth half of what the chamber makes on its own: three of them get two and a half times the power out of the same coal. Whether that shows up as more power or as fuel lasting longer is up to the network, since the chamber already slows itself down when the grid cannot take what it makes. The screen wears the same upgrade strip every other machine does, and the cards drop with the block and travel on a memory card.

### Inscriber

- The Inscriber gained the three buttons [modern Applied Energistics 2](https://github.com/AppliedEnergistics/Applied-Energistics-2) gives it, down the left of its window. **Automation Access Mode** decides whether each face of the machine reaches one part of it - top and bottom for the plates, the other four for the input and the result - or whether every face reaches all of it. **Auto-Export** hands the finished item to whatever inventory is against the machine, a face at a time, skipping the plates' own two faces while the faces are kept separate. **Input Slot Stack Size** lets the three input slots hold 1, 4 or 64 rather than the single item they always held, so a hopper can keep the machine fed instead of feeding it one at a time.
- **The default access mode changed: every face now reaches every slot.** That is modern AE2's default and the friendlier one, since a hopper sitting on top of an inscriber could never reach the input slot before. Automation that pulls the presses back out of a machine will stop working, because a combined machine only hands out its result - put the mode back to separate faces with the first button and it behaves exactly as it always did. Inscribers already placed in a world pick up the new defaults, along with a 64-item input buffer.
- Its empty slots now say which faces of the machine reach them, and the answer follows the access mode. A slot with something in it says nothing, because the item's own tooltip is there instead.
- Two things follow from a buffered input slot, and both are fixed here rather than left to bite: a recipe is matched by what is in the slots and no longer by how many, and a press consumes one item from each slot rather than emptying them, so a stack is worked through one at a time. Renaming with a Name Press does the same - it used to build its recipe from the whole stack, which with a buffer would have handed back sixty-four renamed items for the one it consumed.
- The machine only runs while the result would fit. A full output slot used to leave it grinding on with nowhere to put what it made, which cost nothing when the input held one item and would cost a great deal with sixty-four.
- Progress is no longer thrown away when the input slot is topped up. It resets only when the item in a slot actually changes, so feeding a working machine does not send it back to the start.

### Interfaces

- **Blocking mode has a third setting: smart.** Blocking exists so a machine part way through one recipe is not handed a second, but it also refuses to hand that machine another helping of the recipe it is already running - and a machine with an input buffer big enough to take one just stands there instead. The button now cycles off, blocking, smart, where smart blocks everything except a repeat of the last thing that face was given. Taken from GTNewHorizons' Applied Energistics 2 Unofficial, which spends a separate switch on it; the memory is kept **per face** here rather than per interface, because ours looks at up to six machines at once and one memory for all of them would let a repeat of the recipe machine one is running be shoved into machine two on top of what it is running. The same holds a level down: through a ME P2P tunnel the interface has one face and many machines, so each tunnel output keeps its own memory and the tunnel - which already judges blocking per output - makes the exception for the machine actually running the recipe. A face pointed at another network is unaffected: a network is not busy, only full, and a second helping does not empty it. Existing interfaces read back as they were saved - the two old settings kept their names.

- **An interface can be given a picture of its own.** The Pattern Access Terminal, the Interface Configuration Terminal, the screen that asks where to send a pattern and the crafting tree all draw an interface as the machine standing beside it, which says everything until there are six of them along one row of assemblers - or one that feeds nothing yet and is drawn as a blank. The quartz cutting knife's screen carries an icon slot beside the name box now: put any item in it, by hand or by dragging one out of JEI, and the interface is drawn as that everywhere. While the slot is empty it shows the machine's own answer, greyed, so it is plain what clearing it goes back to, and a button beside the name clears the name and the icon together - a right click on either still clears just that one. The picture is kept in the interface and travels with it when it is taken down with a wrench, the way its name always has. The Pattern Access Terminal also stopped putting two differently pictured interfaces under one heading: a row is a name and a picture now, since a player who gave them different ones did it to tell them apart.

### Memory card

- A memory card stored a name it never applied. Every machine copied wrote its custom name into the card's data, and pasting the card read the settings, the filter, the priority and the cards back out and ignored the name entirely - so the field rode along on every copy doing nothing. It is written only onto the item a wrench leaves behind, which is the one place it was ever read.
- **A memory card copies the cards installed in a machine, not only its settings.** Everything else about a bus travelled - the filter, the settings, the priority, the key types - so a copy of a bus with four acceleration cards and a capacity card came out looking identical and working nothing like it, and the cards had to be put in by hand afterwards. They are on the card now, for everything with an upgrade slot: buses, planes, level emitters, both interfaces, the molecular assembler, the IO port. Pasting leaves the machine holding exactly what the copy names - a card it does not name is taken back out - and the cards themselves are real items rather than a number to be conjured: what is missing is drawn from the player's inventory and from a network tool they are carrying, what is taken out is handed back the same way, and anything neither will hold falls at the player's feet. In creative mode the set is simply applied, free. If the player is short of a card, the rest are installed and one line says so, the way copying patterns has always said it. The cards are restored before the filter and before any patterns, because how many slots a machine offers for either is decided by the cards standing in it. Copying upgrades with a memory card is behaviour taken from [modern Applied Energistics 2](https://github.com/AppliedEnergistics/Applied-Energistics-2), which also reaches into the network tool for them.
- The priority a machine orders its crafts at travels with the rest. An export bus, an interface or a formation plane carrying a crafting card has two priorities - the one that ranks it against other machines for storage, and the one its jobs are queued at - and only the first was on the card, so a copied machine went on ordering at whatever it had. A card written before this says nothing about the craft priority rather than zero, so pasting an old one leaves it alone.
- The card itself says what it carries: a copy holding cards or patterns names how many of each under the name of the machine it was taken from, since pasting it now costs the player those items.

### Networking

- How many channels a node carries is no longer one of two fixed sizes. Every cable, controller face, quantum bridge and P2P tunnel now names a **channel tier**, and each tier's number is read from the `ChannelTiers` section of the config, where `0` carries nothing and `-1` means the node imposes no limit of its own. An addon registers its own tier through `IChannelTierRegistry` during pre-initialisation and declares it from `IGridBlock.getChannelTier()`, which is all that is needed to ship a cable of any size; the tier appears in the config file by name, so a pack can retune an addon's cable without the addon knowing. A node that names no tier falls back to the `CANNOT_CARRY` and `DENSE_CAPACITY` flags exactly as before.
- A connection is as wide as the narrower of the two nodes it joins, rather than being capped at the dense cable's size whatever it runs between. That cap used to be the real limit on what one controller face gives, which meant the dense cable's setting silently governed the controller as well; a controller face now has a tier of its own, unlimited by default, so what a face gives is decided by the cable plugged into it. Nothing changes at the sizes AE2UD ships - the largest cable is still the dense one at 32 - and it is what lets a larger cable from an addon actually carry what it says.
- A cable's item tooltip says how many channels it carries, so the number can be read at a crafting bench rather than only from a placed cable, and a pack that changed it says so. Waila and The One Probe used to work the same number out from the cable's class, which was wrong for anything an addon shipped and silently showed nothing at all for one that was not ours; both ask the cable now.
- A smart cable's channel indicator is drawn as a fraction of what that cable carries rather than of what a normal cable carries, so a larger cable no longer looks permanently full. Setting a cable below its stock size also used to divide by zero and take the client down with it - the eight marks are scaled now, not divided into.
- The thickness a bus adds to the cable it sits on was measured against the number of channels a normal cable carries. Both happened to be 8, so it worked; the two are unrelated, and lowering that setting made buses stop drawing their collar.
- The quantum bridge and the ME P2P tunnel stop borrowing the dense cable's number. The bridge has a tier of its own, still 32, covering all nine blocks of a ring - everything crossing it funnels through the centre, and cables reach only the four side blocks, so there is no single cable for it to defer to. The tunnel is the opposite case: exactly one cable at either end, so it now imposes no limit of its own and carries whatever the narrower of those two allows. With the cables AE2UD ships that is the same 32 as before.
- What an ME P2P tunnel **costs** the network it sits in is now `p2pTunnelChannelCost` in the config's `general` section, still 1. It was the one number in this whole subsystem a pack could not touch, and the tunnel becoming as wide as its cables is what made it worth pricing.
- How many channels a network with no controller carries is now `adHocNetworkChannels`, still 8. It used to be the normal cable's capacity, so raising that raised this by accident.
- **The `normalChannelCapacity` and `denseChannelCapacity` settings are gone.** They are now the `appliedenergistics2:normal` and `appliedenergistics2:dense` lines of the `ChannelTiers` section, and the old keys are not read - a pack that changed either of them has to set the new one, or it goes back to 8 and 32.

### Planes and buses

- **A storage bus can be told which key types it stores.** The second button beside its window opens the same type picker the import bus and the terminals already use, and a type turned off there is neither reported to the network nor accepted into whatever the bus is pointed at, as though that block had never held the type at all. A tank sitting inside a chest, a machine that shows both an item and a fluid side, or a bus mounting another ME network whose fluids should stay in it - all of them used to be all or nothing. The choice holds however the storage was resolved: the per-type strategies that read an ordinary block simply leave the disabled ones out, while another ME network and a Storage Drawers repository, which hand back one storage with no seam to leave anything out of, are filtered on the way out. At least one type is always on, and a bus placed before this keeps acting on everything. Filter slots are left alone - a fluid named in the filter of a bus with fluids turned off is simply never matched, and turning the type back on brings it back. Modern AE2 offers this picker on an import bus and an ME chest, but not on a storage bus.
- The picker now names what it is for rather than guessing. It carried two sets of words - a terminal saying "Visible Types", a bus saying "Imported Types" - and chose between them by asking whether changing the selection needed build permission, which is a different question that happened to have the same answer twice. A machine says which of the three it is, and a storage bus says "Stored Types". The three buttons also stop borrowing the wrench that means priority and partitioning, and wear a list instead.
- A filter naming a key type its bus is set to ignore is greyed out, the way every slot greys when the network is dark, and says why when the cursor rests on it. Nothing about the filter changes - it is kept, and means what it always did the moment the type is turned back on - but until then the bus walks past it, and the screen had no way of saying so. This was already true of an import bus, whose type picker has been there since the buses learned about types, and where a filtered fluid simply stopped being imported with nothing on screen to explain it.
- **A formation plane can be told which key types it places.** It builds one placement strategy per registered type and hands each key to whichever answers, so a plane with an empty filter accepted anything the network cared to push at it - there was no way to say "blocks, but never fluids" short of naming every block in the filter. The button is the same picker, and a type turned off is left out when the strategies are built, so the plane simply reports back that it took nothing. Its window says "Placed Types" rather than borrowing the words meant for a bus. Both planes list only the types they could act on at all - a type an addon registers without a placement or pickup strategy never appears, since turning it off would change nothing.
- **A formation plane can fetch what it places instead of waiting to be filled.** The button beside its window switches it between passive - mounted in the network as storage, placing whatever is pushed into it, which is how it has always worked and still is by default - and active, where it is no longer storage at all and instead takes what its filter names out of the network, one placement at a time. An empty filter in active mode places nothing: an active plane is told what to put down rather than deciding for itself. The inverter card has nothing to say there either, so it goes on meaning what it means in passive mode. A fuzzy card lets a named item stand for its damage range, an acceleration card multiplies what goes out per operation (which only a stack thrown into the world can use - a block goes down one at a time), and a redstone card gives the plane the switch it never had. The idea, the card set and the acceleration multipliers are [ExtendedAE](https://github.com/GlodBlock/ExtendedAE)'s, whose Active Formation Plane is a separate part; here it is the same plane in another mode.
- The buttons beside a formation plane pack themselves down the column, so a card that is not installed leaves no hole in the middle of it. That packing was written for the import and export buses and lived in their screen alone; every screen of that family shares it now, which is what lets the plane show a redstone button and a fuzzy button that each come and go on their own.
- **An annihilation plane has a window of its own, and a filter in it.** It had neither: it broke whatever it was pointed at, and the only way to make one selective was to point it at something selective. The window is laid out like the formation plane it mirrors - two rows of filter growing to five with capacity cards, five upgrade slots - and an empty filter still means everything, so a plane placed before this behaves exactly as it did. A fuzzy card matches on damage and an inverter card turns the list around into what the plane must leave standing, which is the way most of them will be set up: break everything except the two blocks worth keeping. The plane also gets the type picker, so one that should collect blocks but leave a lake alone can say so.
- A block the filter rejects is left standing rather than broken into nothing. The plane asks whether the whole drop can be stored before it breaks anything, and the filter answers on that same path, so refusing costs the block nothing. A block dropping several things of which one is filtered out is left alone too, for the same reason - the plane never breaks what it cannot take in full.

### Storage cells

- **Storage cells go up to 16384k.** Four tiers above 64k - 256k, 1024k, 4096k and 16384k - for item cells and fluid cells alike, each with its own storage component. The numbers continue the ladder the first four already walk: bytes per type quadruple every step (2,048 up to 131,072) and idle drain rises half an AE per tick (2.5 up to 4.0). Type counts do not move - sixty-three on an item cell, five on a fluid one - because a tier says how much fits, not how many kinds. Every component is three of the tier below plus an engineering processor, which until now was needed for no cell at all, and the housing is the same at every tier: what a cell costs sits in its component. The crafting storage blocks follow their components up the same four tiers, so a crafting CPU can be built out of 16384k blocks - the colour ladder carries on past the 64k block's cyan into azure, blue, violet and pink, since a block has no housing to brighten and only its colour can say which tier it is. One switch, `Features.Storage.HighCapacityStorage`, turns all of it off. The creative tab lists materials in the order they are declared now rather than alphabetically, so the storage components read 1k to 16384k and the presses, prints, processors and cards stand with their own kind. JEI is not affected: it orders an item's subtypes by metadata and nothing a mod does can move them. The tiers and their figures are from [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial), as is the component artwork; the cells themselves wear this fork's own, redrawn from the dense cells of [NAE2](https://github.com/AE2-UEL/NAE2).

- **A cell's tooltip is five lines of contents, not sixty-three.** A full cell printed a line per type, which ran off the top and the bottom of the screen and hid the byte and type counts above it. It now names the five there is most of, largest first, and says how many more there are; the window the view key opens is where the whole list lives, and the tooltip says which key that is. The five are no longer behind Shift either - they were only ever hidden because there were sixty-three of them. A partitioned cell shows its contents like any other: it used to print what it was **set to accept** instead, with nothing on screen saying which of the two lists you were reading. What it accepts is a tab in the window now. A creative cell follows the same rule. The `showCellContentsPreview` option is gone with the problem it existed to work around.

- **A storage cell can be looked into.** Press the view key - the same one that opens an encoded pattern, P unless it has been rebound - over any cell to see what is in it: a storage cell, a portable terminal, the matter cannon's ammunition, the colour applicator's paint, a creative cell's list. The window is the ME terminal's own grid, sorting and search field handed a list that came out of a cell rather than off a network, so it scrolls, sorts by amount and searches with the same syntax; a cell with a filter gets a tab that switches between what it holds and what it accepts, saying which list is which and whether the filter includes or excludes and matches precisely or fuzzily. The cards installed in the cell are shown on a plate against the right edge, exactly as many slots as there are cards. It is read-only and reaches no server at all - a cell carries its contents in its own NBT and the client already has the stack - and it opens over whatever screen you were in and puts that one back when it closes, so looking into a cell never costs the terminal you were browsing.

- **The Equal Distribution Card**, ported from modern upstream AE2. Put it in a cell at a Cell Workbench and the cell is cut into equal shares, one per type, so a single item cannot fill it. How many shares there are is the size of the cell's partition when it has one to count - a fuzzy partition stands for more keys than it lists, so it cannot be counted, and the cell's type limit is used instead. Bytes reserved for the types themselves come off the top first, since no type can spend them. It caps what goes in and nothing else: what is already over its share stays, and taking things out is untouched. Cells, portable cells and the Colour Applicator take it, which for the applicator is the first upgrade card it has ever been offered - its two card slots have been unusable since they were added.
- The share is written on the cell's tooltip, in bytes and beside the number it was divided by - "Equal Distribution: 32,256 Bytes per type (2 of 63)" - because every question about that figure is really a question about the divisor. The divisor is the partition, not what is stored: naming one more type in the partition makes every other type's share smaller. The numbers are sharper than they sound. An unpartitioned 1k cell is cut 63 ways, into 67 items each; the same cell partitioned to four types gets 1,984 each. Partition a cell that carries this card, or it will stop accepting long before it is full.
- **The Overflow Destruction Card**, ported from modern upstream AE2 alongside the one above. A cell carrying it never refuses: what does not fit is destroyed instead of staying in the network. Put it with an equal distribution card and the two compose - the overflow of a type whose share is full is destroyed while the other shares go on filling, which is the pairing upstream documents. It takes the same machines as the distribution card: cells, portable cells and the Colour Applicator.
- The card destroys what overflows, never what the cell refuses on principle. A key type the cell does not serve, a key its partition excludes, one its own blacklist names, and a storage cell that still has something in it are all turned away untouched, as they were before. Upstream destroys that last one: a full cell pushed into an unpartitioned carded cell simply vanishes. An unpartitioned cell that can take no further type also refuses anything it was not already storing, which is upstream's own guard against a full cell eating the whole network.
- A cell carrying the card says so on its tooltip, and says it **in red while the cell is not partitioned** - the difference matters more than the marker does. Partitioned, the card destroys the overflow of the types the player named. Unpartitioned, it destroys the overflow of all sixty-three types the cell happened to pick up, which is nobody's intention and is why the upstream guidebook shouts about partitioning.
- **Cells have more card slots**, because two were already too few: an item cell accepts a fuzzy, an inverter and a sticky card and could hold two of the three. There is a slot per card the cell can take now - five on an item cell, four on a fluid cell, which is never offered the fuzzy card, and four on a portable cell. The workbench already drew as many slots as a cell reported, so nothing about the screen changed, and a cell saved before this keeps the cards it had.

### Terminals

- **The Interface Terminal is now the Pattern Access Terminal**, wired and wireless, which is what upstream calls it. The screen is unchanged; the name is, because what it lists is about to stop being "interfaces" and start being "anything in the network that holds patterns". Nothing placed or held is lost: a part is stored by a number rather than by its name, and that number has not moved. An interface hidden from the terminal stays hidden, and a wireless terminal keeps the mode it paid for, both through a rename the save file is read for. Two things do change under the hood: the recipes name the part as `part.pattern_access_terminal`, so a pack that overrode one has to follow, and the one config switch that used to turn this terminal off is now two - `PatternAccessTerminal` and `InterfaceConfigurationTerminal` - because it had been turning off the Interface Configuration Terminal beside it as well; whichever way the old switch was set, both inherit it. The keyboard shortcut is the one casualty: it is renamed with the terminal, so a key bound to it goes back to its default and has to be set again.

- **Ctrl+middle-click an ingredient in JEI to take it out of your network, Alt+middle-click to order it made** - taken from [RandomComplement](https://github.com/Circulate233/RandomComplement), keys and all. It works over JEI's list and over its bookmarks, from any screen: with an ME terminal open the job goes to that terminal's network, and otherwise to a wireless terminal in your inventory or a bauble slot. Taking gives a full stack, or one with Shift also held, and never more than there is room for - what will not fit is left in the network rather than dropped at your feet. Ordering opens the usual amount screen with the item already filled in, and asks the network whether it can make the thing first, so a click on something no pattern exists for says so in one line instead of walking you through two screens. Fluids can be ordered; they cannot be taken, having nowhere to go. A network with none of the thing says so, and so does an inventory with no room for it - unlike pick block, which stays quiet, this gesture named one thing on purpose and silence would read as a broken key. Both keys are rebindable in the controls screen and both are named in the tooltip of the ingredient they act on - but only when you actually have a network to reach, so the lines are not printed under every item in the list forever. None of it uses JEI's cheat mode, which a server switches off for anyone not in creative. `JeiRetrieve` and `JeiCraftRequest` in the config turn them off. Written up in `docs/NETWORK_SHORTCUTS.md`.

- **The vanilla pick block key takes what your network has**, the way it takes what your inventory has - taken from [RandomComplement](https://github.com/Circulate233/RandomComplement). Middle-click a block you have none of, and a wireless terminal in your inventory or a bauble slot buys it out of the network and puts it in your hand. Nothing changes while the block is somewhere on you: that is still vanilla moving it to hand, and without that rule every click on the stone underfoot would order a stack out of storage. Sneak for one instead of a full stack. It answers for entities as well as blocks, so an item frame or a minecart comes out of storage on the same click. A hand already holding a part of a stack is topped up rather than made to start a second one elsewhere; a hand holding something else takes the first empty slot on the hotbar. The terminal has to be linked, charged and in range, exactly as it does to open, and it says which of those it was not - but never when you carry no terminal at all, and never when the network simply had nothing, since middle-clicking grass is not an error. Each terminal carries its own switch for this, a new button in its left-hand column, so the one on your belt can answer while the spare in a chest does not; `NetworkPickBlock` in the config turns the whole thing off for a pack. Creative is untouched. Written up in `docs/NETWORK_SHORTCUTS.md`.

- **Clicking a search box with something on the cursor searches for it.** Dropping an ingredient from HEI onto the ME terminal's box already did that; a stack held on the cursor had no way in, and the other four boxes had neither. Both ways now go through one list a screen publishes - which box, and what to write in it - so the ME terminal, the cell view, the Crafting Plan's tree, both Recipe boxes of the Pattern Access Terminal and the Interface Configuration Terminal's item box all answer to a drag and to a click alike. The item is only read: it is neither put down nor taken, and the name goes in quoted, as one term, so a space in it stays part of the name. A held bucket searches for the bucket, not for what is in it - the cursor shows a bucket, and that is what HEI hands over for the same drag.

- **A search box can be told to keep what was typed in it, on every screen that has one.** The ME terminal could already do it, through the Search Box Mode setting - which carried eight values because keeping the text was folded into it, giving every mode a `_KEEP` twin. It is its own button now, and the mode setting is back to the four things it actually describes. The same button appears on the cell view, the Crafting Plan's tree and both of the other terminals, none of which could remember a search at all; the Interface Configuration Terminal, which always did whether you wanted it to or not, now asks. One setting answers for all of them, so it is learnt once. A config file written before this says `AUTOSEARCH_KEEP` and the like; it is rewritten into the mode plus the new setting on load, so nothing is silently turned off. The button wears a search box with a padlock on it - shut and still written in, or open and emptied - drawn into the two cells the four dropped modes freed on the icon sheet; the other two are left blank for whatever comes next.

- The Pattern Access Terminal and the Interface Configuration Terminal read the same search grammar the ME terminal does. Each had grown half of one on its own - a space meant AND, `-` or `!` left something out - and the two halves did not even agree with each other: `iron gold` in the Pattern Access Terminal found a pattern using iron **or** gold, while the same words in the Configuration Terminal had to describe one single item. Both now mean what they mean everywhere else, and everything the terminal understands came with them: `"iron ingot"`, `iron | gold`, `@` the mod, `#` the tooltip, `$` the Ore Dictionary, `&` the registry name, and a `/regex/` term. Exclusion keeps the meaning it had - `-iron` finds patterns with no iron in them, which is a question about a whole pattern and not about one ingredient, so the query is asked of a pattern's ingredients as a set rather than one at a time. A query that only says what to leave out no longer paints every remaining slot green: there is nothing it asked to find. The boxes hold a hundred characters instead of twenty-five, hovering one lists the whole syntax, and the guess-cache both screens kept - which assumed one more letter could only ever narrow the result, and so quietly hid matches from any query containing `-` - is gone. Written up in `docs/SEARCH.md`, which is `docs/TERMINAL_SEARCH.md` renamed now that five fields read it.

- **The search box mode button opens a panel instead of stepping through eight settings.** There are eight of them and they are four modes, each of which can also keep what was typed - so half of them differ from a neighbour only in that, and finding the one wanted meant clicking through the rest. Left click now opens them as a grid to the left of the button, a row to a mode with the plain one on the left and the keeping one beside it, so which column is which is learnt once rather than read off each icon; the mode in use is greyed and dead, since clicking it would change nothing. Right click still steps to the next one, the way every setting button in the mod does. The panel opens the way a wireless terminal's mode switch does, and the two shut each other, since they open over the same strip of screen.

- **The terminal search understands a real query now, and it is HadEnoughItems'.** It used to be one prefix and a list of words: `@` on the front of the whole line searched mod ids instead of names, space-separated words all had to match, `-word` and `!word` left something out, and the line was also compiled as a regular expression which was then run over tooltip lines only - a rule nothing said out loud and which quietly turned a name with a bracket in it into a different search. The grammar is HEI's now, character for character: `iron | gold` matches either side, `"iron ingot"` keeps the space inside one term, a backslash escapes whatever follows it, and `-` and `!` still leave things out. Alongside the name there are four channels - `@` the mod, `#` the tooltip, `$` the Ore Dictionary, and `&` or `*` the registry name - and a term in slashes, `/^dense.*plate$/`, is a regular expression, which is what became of the old accidental one. Matching HEI rather than modern upstream AE2 was deliberate: upstream reads `$` as tooltips and `#` as tags, the exact opposite of the field the player types into every day, and under the search-box setting's HEI modes this terminal hands its string straight to HEI, where one string meaning two things would be worse than any grammar. `@` also answers to the mod's name and not only its id, so `@ae2` finds a mod whose id is `appliedenergistics2`, which is how it behaves in HEI and did not here. Whether a plain word also looks inside tooltips is still the terminal's own setting rather than a symbol; `#` asks for tooltips whatever that setting says. The field holds a hundred characters instead of twenty-five, which a query of this shape needs. Ideas taken from [AE2 Improved Search](https://www.curseforge.com/minecraft/mc-mods/ae2-improved-search); the grammar itself is HEI's own. Written up in `docs/TERMINAL_SEARCH.md`.

- The search is also a great deal cheaper. The filter runs again on every update the network sends, and it used to recompile a regular expression, rebuild a localised name and, with tooltip searching on, build a full item tooltip for **every row of the terminal, every time**. The query is parsed once when it changes; what a key answers - its name, its tooltip, its Ore Dictionary names - is worked out once per key and kept, and so is whether it matched. Names are also read without their formatting codes and folded case-insensitively in a fixed locale, so a coloured name no longer hides from a search and a Turkish client no longer fails to match `I` against `i`.

- **A key type can say which Ore Dictionary names it answers to.** `AEKey.getOreDictNames()` is what the `$` channel asks, and it returns nothing unless a type says otherwise; items answer it out of the Ore Dictionary. Upstream's equivalent channel searches item tags, which do not exist on this version. Asking the key rather than testing for an item at the search site is the point: an addon's own key type joins the channel by answering.

- A view cell can be switched off without taking it out: right click it in the terminal's own row of them, the way a magnet card in a wireless terminal has always worked. A cell that is off filters nothing at all - not the list, and not what a recipe transferred from HEI or pulled through a crafting terminal may take out of storage, since all four of those ask the same one method. It says which it is in its tooltip, along with how to change it, and so does the magnet card: that line was grey among grey ones on both, and is green or red now.

- A small lamp burns in the corner of every slot holding something that can be switched off, so its state is read off the screen rather than out of a tooltip: the five view cell slots in a terminal, and the upgrade slots on all four wireless terminals wherever a magnet card sits in one. Red for off, green for on. It is drawn over the slot and over the item in it, in the top right corner, which is the one corner a stack size never uses, and it is only ever looked at - the item under it is still switched by right clicking it as before.

- Highlighting a block now turns the player to face it. The button beside a row in the Pattern Access Terminal and in the Interface Configuration Terminal, and the machine lookup in the Crafting Tree, all used to draw the red outline and close the screen leaving the player looking wherever they had been - which for an interface behind them meant the answer was on screen and invisible. The view snaps to the block the moment the screen closes; where several were highlighted at once, to the nearest. Turn it off with `turnToHighlightedBlock` in the config's `Client` section.

- **A key type can say how it is drawn.** Anywhere a key stands in for an item - a terminal slot, a filter, a tooltip, the crafting tree, an item frame - it is drawn by wrapping it into an item and letting the ordinary item renderer have it. Which model that renderer got was decided by a hardcoded test for a fluid, in two separate places: one chose the geometry, the other the tint. Everything else fell through to the model of the type's button icon, and an addon key type had no way to draw itself at all. There is now `appeng.api.client.AEKeyRendering`, a registry of one `AEKeyRenderHandler` per `AEKeyType`, which supplies the model and the tint; the handler is given an `AEKeyModelContext` that hands back sprites, item models and ready-baked sprite models, so it never touches the mod's own rendering and inherits its caching for free. The fluid handling is the first entry in that registry rather than a branch in the dispatcher, and both hardcoded tests are gone. A type that registers nothing still draws exactly as before, through its button icon, so nothing has to be registered to work. This is the first client-side API AE2UD declares; modern AE2 has one of the same name, but its shape belongs to a render pipeline that does not exist on 1.12.2, so the contract here is the fork's own.

### Tooltips

- **The search grammar hides behind Shift.** Eleven lines opened under every search box the moment the cursor crossed it, on seven boxes across six screens, and covered whatever was under them - a reference nobody needs after the first read, shown as insistently as a warning. Hovering a box now says two lines: what the box searches, and that Shift shows the syntax; hold Shift and the eleven lines are there. The four boxes on the two interface terminals were also opening with their own name and then the word "Search" under it, because the label and the grammar's title were written by two different places; a box gives its name once now. The explanation moved to sit beside the parser that it describes, so a rule added without its line is harder to miss.

- The view cell and the magnet card explained the same right click in two different ways - one said "right click it in a terminal to switch it off or on", the other "right click with an empty hand while equipped on a terminal to toggle ON or OFF". It is one action and it is one line now, kept beside the state line the two already shared, so they cannot drift apart again.

- **Priority says what it decides.** The number was the whole explanation: a box asking for a figure, on six screens, with nothing anywhere saying what a bigger one does. The tab that opens it now spells out both halves of the rule, and the second half is the one nobody knows - a thing is **stored in the highest priority that will take it** and **taken out of the lowest priority that has it**, so a high-priority drive fills first and empties last. Within one priority level, storage already holding the thing is filled before storage that is not. Craft priority is a different number that reads the same way and was equally silent; its button says what it settles now, in three short lines rather than one long one: that a higher number takes the next free machine, and - as the port notes already say - that it never makes a job faster and never picks where a job lands.

- **The terminal's search field says what it understands, and goes red when nothing answers.** Hovering it lists the whole grammar, one line to a rule, with an example on each: several words that all have to match, `iron | gold` for either side, `"iron ingot"` for a term with a space in it, `-stone` or `!stone` to leave something out, then `@ae2` for the mod, `#fortune` for the tooltip, `$ingotIron` for the Ore Dictionary, `&minecraft:stone` for the registry name and `/^dense.*/` for a regular expression. It is drawn by hand rather than through the usual tooltip interface, because a class that is both a text field and a tooltip source crashes outside the development environment. Separately, the text turns red while the query matches nothing at all - the way HEI marks its own field - which is the difference between having typed it wrong and the network really having none of it. A pinned row counts as an answer, since it stays on screen whatever the search says.

- **Slots say what a click on them would do.** A slot shows what it holds and nothing about what can be done to it, and this mod's slots understand a good deal more than picking a thing up. Hovering one now names the clicks that are not obvious: the button muted, the action plain, and the thing it acts on in its own colour - an item in the colour of its rarity, anything else in the colour its key type asks for. A terminal row with a bucket or a tank on the cursor reads "Left-Click: Extract Water" and "Right-Click: Deposit Lava", and an empty container counts as much as a full one - what is asked is whether the thing on the cursor could take what the row holds, so a full bucket over the fluid it already holds is offered nothing. An empty square of the grid is not blank either: there the left click stores the container itself and the right click still pours out what is in it, which is the same ambiguity read the other way round. Holding more than one adds the control lines, which fill or empty the whole stack at once and were invisible before. A filter slot reads which of the two clicks sets the filter to the container and which sets it to the contents, the one pair nothing else could tell apart, and says when it takes a typed amount, since a middle click is not a thing anyone tries. And a filled container lying in the player's own inventory says that shift-right-click pours it into the network and that holding control pours the whole stack, which was the least discoverable action in the mod. Lines appear only where the cursor's present state actually offers the action, so an ordinary item over an ordinary slot gains nothing. The wording is upstream AE2's, key names and all, so a translation of theirs fits ours.

- **An empty slot says what belongs in it.** A slot that only takes one kind of thing looks like every other slot while it stands empty, and the faint icon behind it was the only clue - which asks the player to already know what a Quantum Entangled Singularity looks like at sixteen pixels. All twenty-five kinds of restricted slot name themselves now, so the range booster slot in a Wireless Access Point, the biometric card slot in a Security Station, the fuel slot in a Vibration Chamber and the fifty-odd others say what they want. The line is carried by the kind of slot rather than written at each of the places one is built, so a slot added later explains itself without anyone remembering to say so. A slot with something of its own to say says that instead - the Inscriber's four, which name the side automation may reach them from and whose contents HEI already spells out.

- The sort direction button said the same thing whichever way the list was sorted: "Toggle sorting direction", in both states, on every terminal and on the crafting CPU list. It reads "Smallest first" or "Largest first" now, which is what upstream AE2 puts there and what a setting button is for - saying which state it is in, not what pressing it does.

### Upgrade cards

- **Every upgrade card is redrawn**, the two blank ones included. Sixteen cards had grown up over as many
  releases, some inherited and some added here, and they no longer looked like one set.

### Wireless terminals

- A wireless terminal has three upgrade slots instead of one, and takes two **Energy Cards** beside its magnet card. Each is worth another terminal's charge, so two of them carry three times what the terminal carried empty - a card is one dense energy cell either way, and a terminal starts out with far more than a portable cell does, which is why the same card is worth eight of a cell's. The plate holding the slots is drawn as tall as the terminal has slots, out of the one-slot texture it always used, on all four screens the terminal opens. Right-clicking to switch the magnet card on and off now answers by what is in the slot clicked rather than by which slot was built last, so it keeps working with cards beside it and does nothing to the cards that have no such switch.

- **The Interface Configuration Terminal can be wireless now**, which it never could before - it is the fifth mode, built the same way as the rest: Wireless Receiver, the panel, a Dense Energy Cell, or crafted into a terminal you already have. Its shortcut arrives unbound, since it has no key to inherit.
- **The terminal switches mode from inside its own screen.** A button at the foot of the column down the left of every wireless terminal carries the mode it is in. Left-clicking it steps to the next mode and right-clicking to the one before, wrapping round and skipping the modes you have not unlocked, so the common case is one click and the terminal never closes. Shift-clicking opens the rest of them out to the left instead, to be picked by eye; while that is open the button only shuts it again, so changing your mind cannot change the mode. Modes that have not been unlocked are in there too, greyed, with a tooltip naming what to craft in to get them - a terminal with one mode would otherwise show a single button and nothing on the screen would say that modes exist at all, which is also why an ordinary click on such a terminal opens the list rather than doing nothing. The list is reported to HEI while it is open and the one button while it is shut, so the item list never covers a mode you are reaching for.
- **There is one wireless terminal now, and it switches between modes.** The wireless crafting, pattern and interface terminals are gone as separate items; the terminal you carry holds the modes you have unlocked and opens whichever one it is set to. The idea is taken from [AE2UEL Wireless Universal Terminal](https://github.com/Circulate233/AE2UELWirelessUniversalTerminal) - the principle only, none of its code.
- Which mode you get is decided by the terminal part you build it with, and the four recipes are otherwise unchanged: Wireless Receiver, a terminal part, a Dense Energy Cell. Build it with an ME Pattern Terminal and it comes out knowing patterns. **Adding a mode later costs only that mode's terminal part** - put the terminal and the part in a crafting grid together. The Receiver and the Dense Energy Cell paid for the aerial and the battery, and a second mode is not a second device. The terminal that comes out is the one that went in: same charge, same link to the network, same upgrade cards, and everything each of its modes had stored on it.
- **Wireless terminals already in a world are not lost.** The three old items are still registered, so no save complains and nothing turns to air; they are simply unreachable - no recipe, no creative tab, no HEI entry - and each becomes the one terminal, with its own mode unlocked, the moment a player carries it. Its charge, its link to the network, its upgrade cards and its crafting grid all come across. A plain wireless terminal stays exactly what it was, with the storage mode alone: nobody is given modes they did not build.
- **The keyboard shortcuts are unchanged.** Shift+T, Shift+E, Shift+R and Shift+I still open the storage, crafting, pattern and interface terminals - they find the one terminal now and open it in that mode, and say so if it does not have that mode yet. There is one shortcut per mode, built from the registry, so a mode added by an addon gets one too; those arrive unbound.
- A shortcut looks at every wireless terminal the player is carrying, not just the first one it finds. It used to stop at the first and give up there, so a second terminal that had the mode - or that was the only one still charged - was never reached. When none of them can be opened, the complaint comes from the one that came closest: being out of power is worth saying, and a spare in a backpack that was never linked is not.
- The terminal is named for the mode it is showing - *Wireless Terminal - Patterns* - and its tooltip lists every mode it owns. A mode belonging to an addon that has been taken out is still listed, by name, and comes back working when the addon does: modes are recorded by name, never by number, so nothing shifts underneath them.
- Each mode keeps its own contents. The crafting mode's grid holds real items and the pattern mode's holds ghosts, and on one item they would otherwise be the same nine slots - which would have meant real items becoming a pattern's ingredients and vanishing when it was encoded. Upgrade cards stay shared, since a card is in the device rather than in a mode; the magnet card now works in every mode, where the interface terminal used to refuse it.
- The config switches that used to remove a wireless terminal remove its mode instead. With `WirelessCraftingTerminal` off there is no crafting mode: not in the fan, not in a recipe, and its shortcut reaches nothing - the same absence the missing item used to be. A mode also needs the terminal panel it is the wireless form of, so turning off the panel takes the mode with it.
- **New API: addons can register modes of their own** through `AEApi.instance().registries().wirelessTerminalModes()`, giving a name, an icon, the screen to open and what unlocks it. AE2's own modes go in by exactly the same call. Register during pre-initialisation: the unlocking recipe and the key binding are both built from the registry afterwards, and neither event comes round twice.
- **Breaking:** `IItems.wirelessCraftingTerminal()`, `wirelessPatternTerminal()` and `wirelessInterfaceTerminal()` are gone from the API, along with the internal `Terminal` enum. The items behind them still exist, but nothing outside the mod has business asking for them any more.

### World generation

- **Meteorites are placed from the world seed alone.** Where the next one went used to be decided by measuring the distance to the meteorites already in the ground, which meant the answer depended on the order the world happened to be walked in - two players exploring the same seed from different directions got different worlds, and a pregenerated world differed from one built by walking. The world is cut into square cells of `minMeteoriteDistance` blocks instead, and each cell holds one meteorite at a position drawn from that cell's own seed, so a chunk can answer whether it holds one without knowing anything about its neighbours. Nothing else about a meteorite is left to chance either: its size, the shape of its crater, the scatter around it and what is in its chest all come from one seed of its own rather than from the clock. The idea and the grid are from [GTNewHorizons' AE2 fork](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial/pull/200); the port to this version follows [kurrycat2004's fork](https://github.com/kurrycat2004/Applied-Energistics-2).
- **A meteorite is a structure now, so it is never left cut in half.** It used to be stamped into the chunk it landed in and then replayed into the neighbouring chunks - but only into those that happened to be loaded at that moment, so a meteorite next to unexplored ground was sliced off at the chunk border and stayed that way. It is registered with the game's own structure system now, which remembers what is where and builds each piece as its chunk comes into being, however long that takes. The files AE2 kept its own record in are gone with it: an existing world's are read once, the first time it is loaded, so meteorites left half built years ago finish themselves off if anyone walks there. Two things do not survive that conversion, both for the same reason - a half-built meteorite is finished without waking the blocks around it, and a fluid placed that way will not flow: a crater that was full of lava comes back empty, and one that was going to fill with water does not.
- **How deep a meteorite sits is worked out from the terrain rather than from a fixed height.** It used to start looking at y=180 and walk down fifteen blocks at a time until it found ground it liked, which is why so many of them ended up buried in hillsides. The ground around the landing site is measured and the meteorite is set into the middle of it - by the median rather than the average, so one cliff or one pillar nearby does not drag the whole thing up with it, and leaning the way the ground leans where it is broken. Doing that without loading a chunk needs the terrain to be worked out from the seed, so for the overworld and anything generated like it AE2 now runs the same noise the generator would have run; the log says which dimensions it can do that for. A dimension it cannot falls back to measuring whatever chunks are loaded, and meteorites there are not reproducible - the log says so once, rather than leaving it to be discovered. `meteoriteMaximumSpawnHeight` still holds as a ceiling on the result.
- **Craters vary with the biome.** Half of them are still a plain hole in the ground; the rest may be full of lava, of lava that cooled to obsidian where it lay, of water, of snow or of ice, chosen by how warm and how wet the biome is - no lava crater in a taiga, no snow one in a desert. A crater cut into ground near water fills with it and is walled in so it does not drain down the hillside, and one in an ocean is not dug at all. The scatter thrown out around a crater is chosen by biome too, where it used to be chosen by whichever block the meteorite happened to be sitting on: a meteorite in a plain that landed on a stray patch of sand no longer throws sand about, and a buried one in a desert now does. That is not only tidier - reading the block under it needs the chunk, and needing the chunk is what made the old generator depend on the order the world was walked in.
- **Clusters of meteorites are back.** A meteorite may have one, two or three more beside it, within thirty blocks, which is what `meteoriteClusterChance` has always meant - the odds and the distance are the ones that were there before. What has changed is how: a cluster used to be a candidate that was let through the minimum distance because it happened to land near a meteorite already in the ground, which is exactly the kind of question that made the old generator depend on the order the world was walked in. The companions are decided with the first one, from the same square's seed, and are parts of the same structure, so the game builds them together. Every one of them has its own seed, so a companion is as varied as a meteorite that landed alone, and every one has its own chest. Both forks this was taken from dropped clusters outright when they made placement deterministic; there is no reason they cannot be both.
- **What a meteorite holds is a loot table now**, `appliedenergistics2:meteor_loot`, so a pack can retune it without touching code - the presses, the sky stone and the nuggets were all written into the generator before. Two conditions and two functions came with it, because the vanilla format cannot say what this table needs to say: `check_tally` lets an entry be rolled at most so many times per chest, which is how a pool of four presses rolled four times avoids handing out the same one four times; `feature_enabled` drops a pool whose feature is switched off; `to_random_ore` picks from the ore dictionary, which is the only way to name loot that depends on which mods are installed. They are documented in [docs/LOOT_TABLES.md](docs/LOOT_TABLES.md). Two things changed in passing: a chest can now hold all four presses rather than three at most, and the counter that used to walk the presses in order across a whole world is gone - it was the last thing about a meteorite that depended on how many had been generated before it, which is the opposite of what the rest of this work is for. Taken from [kurrycat2004's fork](https://github.com/kurrycat2004/Applied-Energistics-2).
- **The certus in mineshaft chests is a loot table now, and a good deal less of it.** The two pools were built in code, which meant no resource pack could touch them: a pack that wanted fewer of them had to switch the whole thing off or reach for another mod. They are `appliedenergistics2:inject/mineshaft`, referenced by a single pool added to the vanilla table, so everything that decides what comes out is in the JSON. The numbers changed with the move, because the old ones had never been balanced - the code still carried the note saying so, from 2016. Every abandoned mineshaft chest in the world used to hold one to four certus crystals **and** one to four certus dust, without fail, which is roughly as much as the whole vanilla materials pool gives and made certus a certainty rather than a find. Now half of those chests hold one lot of either: one to four crystals, or one to three dust at a bit under half the weight. Certus grows in stone and never was the bottleneck; this is meant to read as a hint that the mod is installed. Note that a chest rolls its contents the first time it is opened, so this reaches worlds that already exist. Documented in [docs/LOOT_TABLES.md](docs/LOOT_TABLES.md).
- **`/ae2 meteorites` lists where the meteorites around you are**, worked out from the world seed without generating anything or loading a chunk - so it names meteorites that have not been built yet, and can be run the moment a world is made. It takes a range in blocks and defaults to two thousand. This is the only way to actually see that placement depends on the seed and nothing else: run it on two worlds made from the same seed and the lists match, however differently the two were explored. `/ae2 compass` is beside it for the other half of the question.
- **The debug Meteorite Placer chooses its crater.** Sneak and right-click the air to walk through the kinds - none, plain, lava, obsidian, water, snow, ice - and the next one placed is of that kind, which is the only practical way to look at all seven without flying across a world hoping. It also says what it placed and how far the crater reaches. It carves the full height of the world rather than a slice around the click, because a crater is a bowl and everything above its wall has to go, or the meteorite ends up under a ceiling of untouched ground.
- Trees and grass that decoration grew over a crater after it was dug are cleared away, and what a crater breaks no longer drops on the floor. A new `meteoriteGeneratorPriority` decides where AE2 sits among the other world generators in a pack, which matters now that a crater can cut through something another mod has just built. The two debug tools that had no name - the Meteorite Placer and the Eraser - have one, since an item with none reads as its registry id and cannot be searched for.

- **The meteorite compass stopped reading the world to answer.** Every generated chunk was handed to a compass service that walked its whole column - sixteen by sixteen by two hundred and fifty-six block states, in eight jobs on a background thread - looking for a naturally placed Sky Stone Chest, whether or not a meteorite had been anywhere near. On a pregenerating server that was the single most expensive thing this mod did: a profile of one taken while the world was being built spent 8.3% of the entire server thread in that scan alone, which was seven eighths of everything Applied Energistics cost there. Nothing scans a chunk of its own accord now. What the compass can point at is written down when a meteorite is placed and when a natural chest is broken, and the two answers a compass needs - which chunks hold a target, and where the chest is inside one - are read back from that. This is how upstream AE2 has done it for years; the port to this version follows [kurrycat2004's fork](https://github.com/kurrycat2004/Applied-Energistics-2).
- **The record moved into the save itself.** It used to live in memory-mapped files under `AE2/compass` that the mod opened, wrote and closed on its own, which a backup or a world copy had no reason to know about. It is a bitmap per region in the world's own saved data now, written and restored with everything else. A world made before this is converted once, the first time it is loaded, and how far that has got is remembered per save so it is never read twice - without it a world would lose every meteorite it had already found, since nothing rescans a chunk to find them again. Chests placed before the mod marked which ones were natural still count during that conversion.
- **`/ae2 compass` says what the compass believes and what is actually there.** It asks the saved data whether it thinks this chunk holds a target and the chunk whether one is really in it, and prints both: either alone cannot tell a compass that has lost its bearings from a chunk that simply never had a meteorite in it.
- **A compass stops pointing at a chest the moment it is broken.** A client keeps the answer it was given for half a minute rather than asking every frame, so a needle went on pointing at a chest that was no longer there until that lapsed - which reads as a broken compass, not a stale one. The server now throws away every answer it has cached and tells the clients in that world to do the same, whenever a chunk gains or loses a target. Every answer is thrown away rather than only the one from the chunk that changed, because an answer names the nearest target and so may well have named this one from a chunk away. Spatial transfer does the same, since a cell can carry a meteorite's chest off with it.

### Patterns

- **A button beside the encoded pattern slot sends that pattern into the network**, so a pattern no longer has to be carried to the machine it was written for. Taken from [AE2 Auto Pattern Upload](https://github.com/GaLicn/AE2-Auto-Pattern-Upload) - the idea and the shape of it, none of its code. A crafting pattern goes on its own, because there is only one answer worth asking about: an interface standing next to a molecular assembler, or next to anything else that takes plans. Of those it picks the one with the most room, and of those the nearest, so patterns spread over the groups of assemblers instead of filling the first one found. A processing pattern opens a list instead - any interface will run one, and only the player knows which machine it was written for - showing every pattern holder in the network with what it stands beside, what it is called and how many slots it has left - and where an interface works on every side, it is named after the machine that would run this pattern rather than after whichever neighbour comes first, looking through a P2P interface tunnel the way the interface terminal already does. The ones that would actually run this pattern come first and are drawn plainly; the rest are dimmed and cannot be chosen, with a tooltip saying whether the trouble is that nothing beside it would run this pattern or simply that it is full. Shift-clicking the button opens that list for a crafting pattern too. The same pattern twice in one container is refused, since the second copy only eats a slot; the same pattern in a second container is not, because that is how crafting is run on two sets of machines. A successful send empties the slot and clicks, with no chat line - encoding a dozen patterns would fill the log - while every refusal says why. Turn it off with `PatternUpload` under `Features.CraftingFeatures`.

- **The blank pattern slot draws on the network.** Encoding with nothing in that slot now takes one blank pattern out of storage rather than refusing, so a terminal never has to be topped up by hand. The slot counts what there is to encode with rather than what it is holding: with blanks in it, the figure on it is those and the network's added together, and its tooltip states each. While it stands empty it shows the network's own - the blank pattern, its count, and the craftable "+" where the network has none but can make them - and a click on it then reads exactly as a click on a row of the terminal above: left for a stack, right for half, shift for a stack straight into the inventory, shift-right for a single one, shift and the wheel for one at a time, and middle to order a craft of blank patterns. All of that only while the cursor is empty; with blanks in hand the slot takes them as it always has. HEI reads recipes off the slot as it would off any other. Taken from [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial).
- Shift-clicking blank patterns out of the player's own inventory still fills that slot before the network, and now does so on the wireless pattern terminal too. The slot used to be reached through the panel on a cable, which a terminal carried in a bag does not have, and the guard that kept that from crashing also kept the wireless terminal from ever filling its slot: its blanks went straight to storage while the wall-mounted terminal held on to them. The slot is asked for directly now, so both behave the same and nothing has a panel to ask for.
- Undoing an encoded pattern by dropping it on the blank slot is no longer capped at what one slot holds. The blanks that do not fit go into the network, which is where the slot draws them from anyway, so a whole stack of patterns can be given back in a single click.

- A recipe transferred from HEI into a processing pattern now fills the grid from the first slot onwards instead of copying the gaps out of the recipe screen. A machine category that draws its inputs spread across a wider layout was leaving the ingredients scattered through the pattern with empty slots between them. A crafting recipe still keeps its shape, because there the position is the recipe.

- Pressing **P** over an encoded pattern anywhere - the player's own inventory, a chest, an ME terminal row, another mod's screen - opens a read-only view of what it makes and what it takes, so a pattern no longer has to be carried to the pattern terminal just to be read. The key is rebindable from Options - Controls, and the pattern's tooltip names it. Adapted from [ExtendedAE](https://github.com/GlodBlock/ExtendedAE).
- Ingredients sit to the left of an arrow and results to its right, the way a recipe reads everywhere else, with the shorter side centred against the taller one. The arrow is the pattern terminal's own.
- The view sizes itself to the pattern rather than paging, so nothing scrolls at any size. A crafting pattern keeps its grid shape, taken from how many slots the pattern actually has rather than assumed to be three by three, so a pattern encoded on a larger bench by an addon lays out correctly. A processing pattern has no shape to keep, so its ingredients are packed into the fewest rows that hold them and then into the width that leaves the fewest gaps - ten ingredients read as five and five rather than as eight and a stub.
- A crafting pattern's view shows whether it substitutes ingredients and whether it takes fluids out of the containers holding them, as the same two icons the pattern terminal toggles those settings with - lit or unlit, so both states are visible rather than only the one that is on. Hovering either gives the setting's own description, and hovering the fluid one tints the ingredients the network fills in for, in the same green the pattern terminal marks them with while a pattern is being written. A processing pattern does neither, so it shows nothing. Adapted from [ExtendedAE](https://github.com/GlodBlock/ExtendedAE).
- Ingredients sit in real slots, so HEI looks recipes up from them with its own keys, and a fluid reads as the fluid rather than as the placeholder holding it. Clicking one asks HEI directly, the way a click in its own item list does - left for what makes it, right for what it is used for - since a click in a read-only view has nothing else to do. Closing HEI comes back to the pattern, and closing the pattern comes back to where it was opened from.
- Nothing is asked of the server: the recipe is decoded from the pattern the cursor is already on. The screen opens over whichever one was already there and puts it back when it closes, so looking into a pattern does not cost the terminal being browsed.

### Build

- The workflows were updated and taught to cache Gradle. Every action they used had fallen behind far enough that GitHub was forcing them onto a newer Node than they were built for: `checkout` and `upload-artifact` are on v7, `setup-java` on v6, and the release step on v3. `gradle/gradle-build-action` has been superseded by `gradle/actions/setup-gradle`, which no longer takes the Gradle command as an input, so each workflow now runs `./gradlew` itself. The ordinary build had no caching at all and downloaded the Gradle distribution on every run - which is how it came to fail with a reset connection before compiling a line - so it caches the wrapper along with the dependencies. The cache-warming workflow was triggering on pushes to `master`, a branch this repository does not have, so it had never once run.
- Gradle itself now runs on Java 21. RetroFuturaGradle deprecated running it on anything older and its next major version drops that support outright, so the three workflows moved off Java 17 - the build workflow to Temurin as well, since the `adopt` distribution it asked for has no build past Java 16. Building locally needs a JDK 21 for the Gradle process too. Nothing about the mod changed: it is still compiled through a Java 17 toolchain with Jabel and still ships Java 8 bytecode.
- The development client carries the Flare profiler and Chunk Pregenerator, with the two libraries they need to start, so a profile of a world being generated can be taken without building a jar and assembling a pack around it. All four are declared as non-publishable, so they stay out of what the released jar says it depends on.

Adapted from [NovaEngineering's AE2CraftingTree](https://github.com/NovaEngineering-Source/AE2CT-Legacy) and [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial).

Adapted from [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial).

The positions are asked for on the click rather than carried in the tree, which would cost far more than the rare click that wants them.
- A craft node in the tree shows **the machine the pattern would be pushed to** rather than a generic mark, and names it in the tooltip. The ME Interface Terminal and ME Interface Configuration Terminal draw the same machine beside each interface's name.
- Added `ICraftingMedium.getMachineIdentity()` and `getMachineLocation()`, and `ICraftingGrid.getMediums(pattern)`, so an addon's own crafting machine can say what it looks like and where it is. Both medium methods have defaults, so existing addons keep compiling.
- Amounts in the tree are what the job will really do: a pattern that was considered and dropped is left out, an ingredient that was substituted is shown as the item actually taken, and each branch's amount is its per-craft cost times the number of crafts.
- HEI's recipe keybinds, bookmarks and tooltips work over the tree's nodes, over the Crafting Plan and Crafting Status lists, and over the amount screen's slot, through one shared way of asking a screen what the cursor is over.
- The Crafting Plan screen picks its crafting CPU from the same table the Crafting Status screen uses, replacing the "Crafting CPU:" button that could only be cycled one CPU at a time. Its first row, **Automatic**, is the old default: the network chooses a CPU when the job is submitted. The window is shorter by the height that button occupied. Adapted from [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial).
- Both screens now share one table, so a CPU is named by a serial rather than by its position in the list. Previously a CPU appearing or disappearing while the list was open shifted every entry below it, and the selection silently moved to a different CPU.

A CPU with none is left unmarked. Adapted from [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial).

### P2P tunnels

- Added the **ME Interface P2P Tunnel**, which lends an ME Interface's faces to somewhere else: the input stands in front of an interface and every output stands in for it beside a machine of its own, so one interface can drive as many machines as there are outputs. Adapted from [GTNewHorizons' Applied Energistics 2 Unofficial](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial) and [NAE2](https://github.com/AE2-UEL/NAE2).
- The interface sees the tunnel as an ordinary crafting machine standing on that face, so nothing about how it looks for a machine changes. The tunnel hands each pattern to the next output in turn, and every output keeps its own queue of what its machine has not taken yet - a machine that has backed up does not stop the interface feeding the others. Blocking mode is judged per output for the same reason.
- Each output also offers its neighbour the interface's stocked items and fluids, which is how a machine there both draws what the interface stocks and hands its results back. Network access is deliberately not offered: a storage bus on an output would otherwise see the whole network without paying for a channel, which is what the ME P2P Tunnel is for.
- An output may face another tunnel's input, so tunnels chain, stock and results included; a pair pointed at each other is caught rather than recursing forever.
- A terminal lists the interface under the machine its outputs stand beside, naming that machine when every output has the same kind and the tunnel itself when they differ.
- **An ME Interface now attunes a P2P tunnel to this type rather than to the item tunnel.** A hopper, a chest, a storage/import/export bus and the other item-related triggers still give the item tunnel.
- Added `ICraftingMachine.of(tile, side)`, which finds a crafting machine on a neighbour whether it is the block itself or a part on that side of a cable bus. Patterns were offered to block entities only, so a part could never be a crafting machine.

### Storage cells

- **The Creative ME Storage Cell and the Creative ME Fluid Storage Cell have been merged into one.** The surviving Creative ME Storage Cell holds an endless amount of every kind of content at once, items and fluids together, and is configured the same way as before. Mirrors upstream [Applied Energistics 2](https://github.com/AppliedEnergistics/Applied-Energistics-2), which ships a single type-agnostic creative cell. **A Creative ME Fluid Storage Cell already placed in a world disappears when it is loaded, along with what it was set to hold; the ordinary Creative ME Storage Cell replaces it in full.**
- Removed the `IItems.fluidCellCreative()` API definition along with the item.
- A cell no longer declares what it stores through `ICellWorkbenchItem`; that method is gone, and the kind of content a cell holds is now decided by the cell's own partition inventory (`CellConfig`, which takes the key types it accepts) and reported by its contents through the new `StorageCell.getSupportedKeyTypes()`. A cell is free to hold several kinds of content at once.
- The ME Chest asks the installed cell what it can hold instead of reading a type off the cell item: it offers itself to neighbours as a tank when the cell holds fluids, and its input slot accepts whatever the cell would actually take. A creative cell set to a fluid therefore works as a tank, and one set to items does not pretend to be one.
- The IO Port counts a transfer per key rather than per cell, so a cell holding items and fluids together moves an item at a time and a bucket at a time as appropriate.
- **A View Cell can now be filtered by fluids** (and by any content type an addon registers), not by items alone.
- **An addon can now ship a storage cell that holds several kinds of content in one cell.** `IBasicCellItem.getKeyType()` became `getKeyTypes()`, and a cell's bytes are counted per content type - a byte holds eight items or a quarter of a bucket, so each type pays its own way and a byte is never shared between two of them. Every cell AE2UD itself ships names one type, for which the arithmetic is unchanged, and no cell in an existing world needs migrating: what a cell holds has always been saved as the keys themselves, and the totals beside them are only a cache.

The border now belongs to the header, as it does in the ME Interface Terminal, and the rows below the last interface are plain background.

Shift+left-click is unchanged. The same Ctrl-for-the-whole-stack modifier also works when filling or emptying a held stack of containers by left/right-clicking a network row. ## 1.0.0 - 2026-07-31

The initial AE2UD release completed the API-breaking migration from AE2 Unofficial Extended Life to the modern generic storage architecture.

### Generic item and fluid storage

- Replaced the legacy `IAEStack` and storage-channel architecture with the modern type-erased `AEKey`, `AEKeyType`, `GenericStack`, `KeyCounter`, and `MEStorage` model.
- Unified item and fluid handling across storage, terminals, cells, buses, interfaces, monitors, planes, level emitters, crafting, packets, and integrations.
- Added a strategy-based world interaction layer so the same automation parts can support every registered key type.
- Reworked configuration inventories to hold items, fluids, and future key types without fluid placeholder items leaking into normal logic.
- Generic terminals can fill or empty held fluid containers.
- Generic import buses, export buses, storage buses, formation planes, annihilation planes, and level emitters can work with fluids.
- Interfaces can stock, serve, display, and push both items and fluids.
- Interface terminals can configure and display fluids directly.
- Fluid ingredients in processing patterns can be delivered to machines.
- Removed the now-redundant legacy fluid terminals, fluid buses, fluid interfaces, fluid planes, and fluid level emitters after their functionality moved into the generic implementations.
- Removed the Identity Annihilation Plane.

- Legacy fluid placeholders in existing configuration data are recognised and converted for display and use.
- Filter and card slots no longer display or retain meaningless stack counts.
- Shift tooltips show the exact configured amount using the key type's own unit and formatting.
